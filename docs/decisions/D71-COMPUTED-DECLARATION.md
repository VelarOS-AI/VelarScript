# D71 — `computed` 成为声明，函数改名 `cached`（用户裁决 2026-08-16）

---

## 前置更正：这是一次**推翻**，不是填一个空白

用户说「之前确实没有考虑到这个问题」。**事实不是这样，我必须先说清楚。**

`computed name = expression` **存在过**，是在响应式系统重写（W-124）时
**被有意移除的**。记录在 `archive/HANDOFF.md:2376`：

> 源语言现在只有一个派生值入口：`computed(() => value)` 返回 `() -> value`
> accessor。**旧 `computed name = value` declaration 被干净移除**并得到单一
> `VEL5055` 迁移诊断

charter:2917 至今写着「**The removed** `computed name = expression` declaration
has no compatibility alias」。**今天拦住它的 VEL5055，正是那次退役留下的迁移诊断。**

当初的理由是规则 3，而它成立：当时确实有两种声明派生值的写法，退役一种是对的。

**本条不重开那个问题，只换答案** —— 并且用改名而不是退役来消除冲突，
所以规则 3 仍然成立（见第 184 条）。

### 当初没有的证据

**这个不对称会制造一类真实缺陷。** D69（`watch total:` 静默死块）与
D70（setup 里的冻结读取）是同一个不对称的两个后果，
而两者都是在**真实产品**里撞出来的 —— 官网的语言切换只切了正文，
英文读者看到中文侧栏。

「一个概念一个拼写」当初挑了**实现更自然**的那一边；
现在有证据表明另一边才是**读者更自然**的那一边。

## 第 182 条 —— 反应层的四格网格

### 用户的话

> 重新用 `state` 声明一个响应式变量不行吗，和 `let` 的用法一致

`state` 今天已经是 `let` 的形状（实测：`=`、`+=`、带标注全部成立）。缺的是另一半：

| | 不反应式 | 反应式 |
|---|---|---|
| **可写** | `let` | `state` |
| **只读 / 派生** | `const` | **`computed`** |

**`state` 之于 `let`，正如 `computed` 之于 `const`。**

### 但真正的理由不是网格好看，是 `const` 不再可信

用户的原话是「**`const` 声明的变量不应该和响应式挂钩，这是最膈应的地方**」，
这比对称性准得多：

```velar
const frozen = locale.text("English", "中文")    // 冻住的
const total  = computed(() => count * 2)         // 活的
```

**同一个词，一个死一个活** —— 于是 `const` **不携带任何信息**。
读者看到它，不知道这个值会不会变。

改完之后 `const` 从「什么都不说」变成「**我保证它不变**」。
**这才是收益：那个词重新变得可信。**

### 它从源头消掉 D69 的陷阱

`watch total:` 不是作者粗心 —— **它是被这个不对称制造出来的**：
一个从 `state` 学会「反应式的东西直接读」的作者，碰到 `computed`
时被要求改用调用，于是漏掉括号。声明化之后 `watch doubled:` 自然就对。

D69 的规则仍然需要（`watch 5:` 还是死的），但它最可能命中的那个真实笔误蒸发了。
**设计修复优于诊断修复：诊断在错误发生后教你，设计让错误不发生。**

### 但它修不了 D70

D70 那个 bug 里**根本没有 `computed`**：

```velar
const localized = items.map(...)      // 普通 const，冻结是因为读取发生在 setup
```

**本条与 D70 无关，D70 仍然要靠那条「发散时报警」的运行时检测。**
（这两件事我一度混在一起讲，是错的。）

## 第 183 条 —— 函数改名 `cached`，不退役

### 用户裁决

> 用户完全可以自己决定要不要用，但是声明必须用 computed
> …换个函数名，别冲突

**语言只规定「声明只有一种写法」；那个函数是工具，不是规定。**

### 实测：三处能力普通 lambda 全都能做

函数形态今天能做而声明形态做不到的三件事，我逐个测了：

| 场景 | `computed(…)` | 普通 lambda `() => E` |
|---|---|---|
| 记录字段 `{read: …}` | ✓ | **✓** |
| 工厂返回一个活读取器 | ✓ | **✓** |
| 条件/表达式位置 | ✓ | **✓** |

**所以函数唯一不可替代的贡献是缓存** —— 这正是用户的判断
（「那个函数我感觉更多的作用是缓存」）。

### 于是名字要说出它真正做的事：`cached`

选 `cached` 不选 `memo`：

- **形状与既有命名一致** —— `sorted()` 给你一个 sorted 的东西，
  `reversed()` 给你一个 reversed 的东西，`cached()` 给你一个 cached 的读取器。
- **房规是平白英语压过术语**（`not`/`and`/`or` 而不是符号；`Look.` 为可读性退役）。
  `memo` 的程序员先验更强，但**读的那一半可能不是程序员** ——
  `memo(() => …)` 什么也没告诉他，`cached(() => …)` 一眼就懂。

### 记录：我一度主张退役，被推翻，理由留着

我曾主张连函数一起退役，论据是「缓存是优化，而项目的优化分层原则说
可选 API 只在有真实证据表明自动的覆盖不了时才加，且仓内零处使用表达式形态」。

**用户推翻，理由成立**：那条规则管的是**「要不要加」一个可选 API**，
不是**「要不要拆掉」一个已经存在、仍然可用、拆除本身有代价的东西**。
**我把规则用反了方向。**

留着这段，是因为将来有人可能照我那条错推理再拆一次。

## 第 184 条 —— 最终形态

```velar
state    count   = 0              // 可写、反应式
computed doubled = count * 2      // 只读、反应式、裸读 —— 声明派生值的唯一写法
const    frozen  = count * 2      // 只读、非反应式，算一次

cached(() => E)                   // 一个能传的、带缓存的读取器
() => E                           // 一个能传的读取器，不带缓存
```

**四个词四件事，`const` 重新可信，而 `computed` 只做一个语法角色。**

### 被拒绝的写法与它们的教法

| 写法 | 处置 |
|---|---|
| `const x = computed(…)` / `let x = …` | **拒绝**，教 `computed x = E` |
| `computed(() => E)`（函数形态） | **退役**，教 `cached(() => E)` 或 `computed x = E` |

**不禁嵌套**：`const bag = {read: cached(() => count)}` 合法 ——
那个 `const` 绑的是记录，不是派生值本身，而且读它是 `bag.read()`，调用看得见。

## 迁移

**面**：`examples/` 与 `docs/` 共 **21 处** `computed(`，**全部是
`const X = computed(…)` + `X()` 的形状** —— 我逐个查过，
**没有一处把访问器当值传递**。

**跨模块导出**从 `export const openTasks: () -> number = computed(...)`
变成 `export computed openTasks = …`，导入方从 `openTasks()` 变成裸读。
**机制现成** —— `export state` 的跨模块反应式裸读今天就在工作。

### `velar fix` 的两类

- **机械（进 `velar fix`）**：`const x = computed(() => E)` → `computed x = E`
  连同 `x()` → `x`；表达式位置的 `computed(…)` → `cached(…)`（纯改名）。
- **需要判断（只给诊断）**：若某处真的把访问器当值传给了别人，
  改法取决于它要不要缓存 —— `velar fix` **不许猜**。
  （与 D58 更正二同一条纪律：不让 `velar fix` 改它证不了的东西。）

## 实施要求

1. `computed name = <expr>` 成为 web 扩展的**声明形式**，与 `state` 同一套解析路径。
2. **裸读**，与 `state` 同形；**不可赋值**（它是派生的，赋值要报错并说明）。
3. 三种作用域与 `state` 一致（模块级 / 组件级 / 块级），**逐一对齐**。
4. **跨模块**：`export computed` 的裸读，机制照 `export state`。
5. `computed(…)` 函数改名 `cached(…)`；`computed` 这个词**只作声明关键字**。
6. `const`/`let` 直接绑 `cached(…)` 是否也该拒绝？——
   **不拒绝**：那是一个访问器值，读它是 `x()`，调用看得见，
   与 `const bag = {read: cached(…)}` 同理。**但要有测试钉住这个判断。**
7. `watch` 与 D69 一并处理；D69 的规则落地后只剩字面量与非反应式 const。
8. charter §15、简报、展示 `03-state-and-derived.vel` 全部更新；
   **展示要把四格网格并排写出来**，那正是本条要教会读者的东西。
9. `readonly` 与 `computed` 的关系：派生值是否自动 readonly 投影？
   **实施者调查后上报**，不要默认。
