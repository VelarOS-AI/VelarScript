# D80 — 官网门禁的两处失明（波 W1 实测 2026-08-16）

官网的 `samples:check` **绿了很久，而它验的是一门已经不存在的语言。**
换上当前编译器之后**立刻红，退出码 1，16 个样例失败**。

这是缺陷族 #2（门禁覆盖面低于自称）最严重的一种形态 ——
不是"漏了一个情形"，是**整门语言落后了一整轮**。

---

## 第 200 条 —— 工具链钉的是一个不存在的版本，没有任何东西盯着它

### 事实

- `package.json` 钉 `@velarscript/cli 0.10.0`、`@velarscript/web 0.10.0`。
- **npm 上没有这两个包**（registry publication deferred，见语言仓
  `docs/contributing/release-process.md`）。
- 实际装的是 `npm run bootstrap:local -- /path/to/VelarScript` 从本地源码构建的产物，
  **而这一步是手动的**。
- 所以 `node_modules` 里那份编译器**停在谁最后一次手动 bootstrap 的那一刻**，
  之后语言改多少次都不会有人知道。

### 它掩盖了什么（W1 换完编译器后的完整红名单）

| 类别 | 数量 | 性质 |
|---|---|---|
| 退役的 `computed(` 调用 | 11 | 样例过时 |
| **反转的反例** | 1 | 页面把**正确写法当错误发布** |
| **D74 可变 prop** | 3 | **正文也错** —— 见下 |
| D72 Web 类型名冲突 | 1 | `VEL5065 'Event' is a Web type name` |
| Desktop 枚举长出两个成员 | 1 | `VEL4015 missing: fix, package` |

**最重的是那三条 D74**，因为错的不只是样例，是**承诺**：
官网当时在发布一条语言已经**主动撤销**的无条件保证
（对照表写着「顶层：编译错误。嵌套：编译错误。」，
章节标题写着「子组件不能改它收到的东西」，
另一处写着 record prop 以传递只读视图到达）。

**过时的样例是 bug；过时的保证是一条语言不再遵守的承诺。**

### 裁决方向（我的建议，待你定）

**让"工具链与语言仓一致"成为门禁，而不是一道人工步骤。**
三个候选，我倾向第一个：

1. **`samples:check` 开跑前先断言装着的编译器与语言仓 HEAD 同源**
   （比对构建指纹或 commit），不一致就红并提示 `bootstrap:local`。
   代价：官网从此需要能看到语言仓的路径。
2. 发布到 npm 之后改回真钉版本 —— **但这只把问题推迟到下一次语言改动**，
   钉住的版本一样会落后，只是落后得更体面。
3. CI 手动钉 ref（现状）—— **已被本条证伪**，它正是漂移发生的地方。

## 第 201 条 —— 反例门禁只要求"引用的诊断码出现过"，不要求"只出现这些"

### 实测

`src/pages/language-records.vel` 的 `commonFieldErrorCode`
**通过了门禁，同时静默发射着 VEL5065**，而它想教的是 VEL4001。
门禁只检查被引用的码**出现过**，所以**一个想教一条错误、实际教了两条的反例，
可以一直绿着**。

还有一条**门禁按现状根本抓不到**：`web-overview.vel` 的
`reservedErrorOutput` 发布 `VEL3007: 'computed' is a reserved extension binding`，
**当前编译器不再发这条**（`computed` 是上下文关键字，保留位归了 `cached`），
而它绿着的原因是 —— **旁边那行 `tick` 仍然产出 VEL3007**。

### 裁决方向（我的建议）

**反例的断言应当是集合相等，不是包含。** 引用了哪些码，
就必须**恰好**发射哪些码；多出来的一条要么写进去，要么就是这个反例写错了。
这同时把上面那条「靠邻居顶包」的情形一并关掉。

**注意这两条是同一个形状**：断言写成了"存在"，而正确的断言是"恰好"。
本仓 D57 第 140 条的标准模块表面审计当初也是这么错的
（子串断言假装在验链接），**是同一族的第三次出现**。

## 一条观察，不是缺陷，不在本条范围

`<Head title={…}>` 在切换语言时**不会重新应用** ——
文档标题停在页面首次加载时的那门语言。W1 确认这是**既有行为且全站一致**
（`/evidence` 表现相同），**且没有触发冻结读取告警**，
所以它是 `Head` 自己的 apply-once 行为，不是 D70 的冻结 `const`。

**记它是因为它和状态章开篇讲的侧边栏 bug 是同一类**，
而语言恰好为那一类提供了工具 —— 值得单独查一次 `Head` 该不该跟随。
