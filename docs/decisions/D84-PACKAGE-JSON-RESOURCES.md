# D84 — 包内 JSON 资源声明、复制与导入（用户裁决 2026-08-20）

这是一份已实施裁决的历史记录。当前语言契约见
[语言宪章](../language-charter.md)，发布契约见
[工具链分发](../package-distribution.md#package-resources)。

## 问题

0.10.4 只能把带 `velar.entry` 的包视为一个 VelarScript 源入口，不能把包内
JSON 作为独立的公共子路径导入。测试沙箱又把包清单重写成单一入口，既丢失
子路径导出，也没有复制资源文件。消费者只能维护一层手工读取、复制和校验的
兼容代码，而 `check`、`test`、`dev` 与 `build` 看到的包并不是同一个图。

## 裁决

1. `import json value from "specifier"` 是 Core 的一等资源导入；`json` 只在
   这个形状中是上下文关键字，其他名字位置仍可使用。
2. JSON 导入值恒为 `unknown`。语言不从外部数据推断可信记录；应用必须用
   Runtime Type 的 `.parse()` 或 `.is()` 建立契约。
3. 项目相对 JSON 必须包含在源根中。包资源必须由 `velar.resources` 用精确
   子路径映射到规范化包内 `.json` 路径，并由 npm `exports` 的同一子路径逐个
   条件指向同一文件。
4. 资源解析拒绝通配符、目录穿越、符号链接、链接逃逸、非普通文件、无效 JSON、
   超过 4 MiB 的单文件，以及超过 128 个声明或 1024 个已导入资源的图。
5. `check`、`run`、`test`、`dev` 和 `build` 共享同一个已校验资源图。测试沙箱
   重建用到的包子路径导出；开发服务器监听并提供资源；无框架输出复制原始字节
   与 ESM 包装；浏览器输出把已校验 JSON 打入 bundle。
6. 0.10.4 消费者的临时兼容层暂不删除。只有它们升级并验证新工具链后，才由各
   自仓库独立移除，避免把语言发布和应用迁移绑成一次不可回滚变更。

## 完成判据

真实跨包样例必须在 `check`、`test`、`run`、无框架构建、浏览器开发服务器和
浏览器生产构建中读取同一份 JSON；沙箱保留资源子路径；非法 JSON 和清单/导出
不一致必须在运行前失败；发行门禁必须验证资源文件确实进入 npm tarball。
