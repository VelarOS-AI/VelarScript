# D97 — 编译产物运行时卫生与整数 range 校验

## 问题

OpenVoxel 的世界生成热路径暴露了两类编译产物问题：

1. 直接 `for value in range(...)` 已经降级为原生计数循环，但运行时会先逐步
   重放完整范围来验证上限，并为三个边界值创建、冻结一份临时 List。大量嵌套
   小循环承担重复分配，大整数范围则在真正进入循环前先执行同量级工作。
2. 项目模式按需导入共享运行时，但需求收集发生在局部记录辅助函数生成之前。
   一个两字段 `Type.from(...)` 因此会导入整套 List、Set、Map 和 Record 主机
   能力；只用于类型分析而没有运行时检查的模块还会生成 `import { }`。
3. 普通 VelarScript import 原样保留每个名字，即使其中一部分只服务于擦除后的
   类型注解；共享响应式桥也会在记录投影只读一个字段时导入全部九项操作。

这些代码不改变程序结果，却扩大生成文件、妨碍审阅，并把本应为常数时间的整数
范围校验留在世界生成等真实热路径上。

## 裁决

- 有限安全整数的直接 range 使用精确算术计算迭代次数；超过一百万项时仍在
  循环体执行前失败。浮点数、超出安全整数范围的数和可能无法前进的步长继续走
  逐步校验路径，保持原有错误语义。
- 计数 range 返回的三个边界值只在编译器生成代码内部立即解包，不冻结，也不
  暴露给 VelarScript 程序。
- 普通 `range(...)` List 只有在生成代码真正引用它时才导入；直接计数循环只
  导入其专用所有者。
- 共享运行时命名导入必须至少包含一个实际引用。记录投影、受控记录构造和绑定
  模式分别声明自己需要的主机操作，不得用“需要集合基础设施”代替精确依赖。
- 响应式桥按生成代码和局部辅助函数的实际引用选择名字；例如纯 `Type.from`
  投影只导入 `reactiveCollectionRead`。
- 只出现在注解里的 VelarScript 导入名不进入 JavaScript 命名导入；模块仍以
  副作用 import 求值。运行时类型复制计划和泛型实例访问器也参加引用收集，
  不能把间接使用的类型身份误擦除。
- `Type.from`、同步记录构造和异步记录构造只生成当前模块会调用的辅助函数。

## 验证

- 编译器测试覆盖直接 range、range 作为值、外部记录 Type 投影、响应式桥、
  注解专用导入、运行时继承复制计划、空导入和无关集合主机能力。
- 性能门覆盖 1000 次约十万步整数范围校验，防止恢复逐步预扫描。
- OpenVoxel 重新构建后检查生成文件中不存在空命名导入，并比较世界生成校验和、
  分阶段耗时与产物体积。
