# D89：建议通道与外语反射拦截（2026-08-20）

## 结论

VelarScript 增加**第二条诊断通道**：`advisories`（建议）。它与现有的
`diagnostics`（错误）并行、独立、互不干扰，**永不阻止代码生成**。

建议**可以被抑制，但抑制必须带上理由**：不带理由的抑制是编译错误。

首批建议只覆盖一类目标：**模型带着 Python / JavaScript 的反射写出来、
Vel 却静默接受成别的意思的拼写**。这类写法无法静态断定，因此既不能沉默
（正是语言定位要消灭的东西），也不能拒绝（会误伤合法源码）。二元的
"静默 / 拒绝"逼出的是坏选择；建议是第三档。

## 为什么这一档在 Vel 成立，而在别处不成立

普通语言里的警告没有用，因为读者是人，人会视而不见，警告会堆积成噪音。

Vel 的读者是模型：模型写代码 → 编译器出诊断 → 模型读诊断 → 模型改。
在这个回路里，建议**有一个必定会读它、并且会据此改代码的读者**。这是
定位（模型写、人读结果、编译器守）第一次为语言争取到一个新的诊断档位，
而不是引进一个人类语言的坏习惯。

配套要求见「门禁与 AGENTS.md」一节：建议之所以有效，是因为
`AGENTS.md` 把"清掉建议"写成交付的一部分，而不是因为它能让构建变红。

## 为什么是独立通道，而不是给 `Diagnostic` 加 `severity` 字段

三条，都是实测出来的，不是偏好：

1. **`diagnostics.length` 现在被当游标用。** `analyzer.ts:3496`、`:3549`、
   `:6964`、`:12573` 和 `web/analyzer.ts:1063` 都在用数组长度判断"这一段
   是不是已经报过了"。把建议混进同一个数组，一条建议会被误认成"已诊断"，
   **把它后面真正的错误压掉**。这是加 severity 字段无法回避的。
2. **总闸保持一字不改。** `index.ts:223` 的
   `diagnostics.length === 0 ? emitter.emit(...) : null` 原样保留。
   建议在物理上不可能挡住代码生成，也不可能被一次重构不小心变成致命的。
3. **纯增量。** 十三个 CLI 消费点、语言服务、`check:docs`、`check:tour`
   全部无需改动即可继续正确工作；接建议是选择性的。

## 抑制：必须署明理由

一条建议可以被就地抑制，拼写是行尾注释：

<!-- velar-preamble
const total = 10
-->
```velar fragment
const step = total // 2   // velar-allow A1: 2 是流程编号，不是除数
```

规则：

1. **必须点名建议编号。** `velar-allow` 后面要跟具体编号（`A1`、`A2`…）。
   没有笼统的"这一行全闭嘴"——那会连带盖掉同一行上别的建议。
2. **必须给理由。** 冒号后面必须有非空文本。
   **`// velar-allow A1` 不带理由是编译错误**（`diagnostics` 通道，
   会让构建失败），不是建议。这是"否则不通过"的落点。
3. **过期的抑制是编译错误。** 写了 `velar-allow A1` 而该行并没有触发
   A1，同样进 `diagnostics` 通道失败。抑制不许烂在文件里骗后来的读者；
   这一条照搬 TypeScript `@ts-expect-error` 的做法，而不是 eslint 那种
   放任不管的做法。

**求值顺序（实施波的调研发现规格在此自相矛盾，此处补齐）：**
`total // 2   // velar-allow A1: 理由` 整条尾巴是**同一个注释 token**——
第一个 `//` 之后直到行尾都是注释体，不存在"第二个注释"。因此：

1. 先从注释体尾部剥离 `velar-allow <CODE>: <理由>` 子句；
2. **再**用剩下的内容判定 A1 的"不含字母"条件。

否则 A1 在 D89 自己的示例上就不会触发，抑制随即被规则 3 判为过期抑制而
报错。抑制扫描器必须在注释体**内部**查找 `velar-allow`，而不是期待一个
独立的注释 token。

为什么理由是真的门槛，而不是形式主义：

- **理由会落进 diff。** 一次静默的闭嘴被换成一句公开的、可复核的声明，
  人在 code review 里看得见。
- **写理由迫使模型先判断。** 模型要写出"为什么这是对的"，就必须先真的
  检查一遍自己是不是写错了；真写错的时候，改代码比编理由更省力。
- **规则 1 与 3 挡住了滥用的最短路径**：不能笼统闭嘴，不能空手闭嘴，
  不能留着过期的闭嘴。

代价是模型可能写出听起来合理的假理由。这个残余风险由**准入门槛**兜住：
一条建议只有在"换成不含糊的写法零成本"时才允许存在（见下），所以正当
的抑制本来就应该很罕见——一片 `velar-allow` 本身就是一个显眼的复核信号。

## 建议的准入门槛

新增一条建议必须同时满足：

1. **有外语反射作为来源**：这个写法是 Python 或 JavaScript 的既有习惯，
   模型有真实的理由写出它；
2. **Vel 静默接受成别的意思**：不是报错，是跑出另一个结果；
3. **触发条件可以收窄到近乎无误报**：条件写得出来、可测试；
4. **零成本改写存在**：建议里必须给出那条不含糊的写法。

不满足第 3 或第 4 条的，不进这一档——沉默或拒绝，二选一，按老规矩办。

## 首批名册

### A1 `//` 后跟纯算式（Python 地板除）

`//` 是 Vel 唯一的注释拼写（`#` 不是注释，见 VEL1005），因此不能靠删除
拼写来消除这个陷阱，只能靠建议。

- **触发**：`//` 之前是一个语法完整的表达式或赋值；且 `//` 之后到行尾
  的内容**只由数字、空白和算术运算符组成，不含任何字母**。
- **不触发**：`// 2. 然后处理 X`（含字母）、`// TODO`、`//` 空注释、
  整行注释（`//` 前无表达式）。
- **消息**：这行的 `//` 是注释，`half` 拿到的是 `total`；如果要地板除，
  写 `(total / 2).floor()`。

### A2 两槽 `for` 的槽位写反

Vel 的两槽 `for` 对 List/Set/字符串是 `值, 下标`（与 JS 的
`forEach((v, i) => …)` 一致，与 Python `enumerate` 相反）。Python 侧的
正确反射 `enumerate(...)` 已经是响亮的错误，不会静默；静默只发生在模型
写出 `for i, v in nums` 这个 Python 和 JS 都不存在的杂交体时。

- **触发**：遍历对象为 List / Set / 字符串；**且**第一个绑定名属于下标
  名册 `i`、`idx`、`index`、`pos`、`position`；**且**第二个绑定名属于
  值名册 `v`、`value`、`item`、`el`、`element`，或是遍历对象名的单数形。
  两条名册必须同时命中。
- **消息**：两槽 `for` 给出的是 `值, 下标`；这里 `i` 拿到的是值。
- **交换两个名字只作为编辑器快速修复提供，不进 `velar fix`。** D38 §48
  把注册的机械修复限定为"不涉及判断"的改写，而交换绑定名恰恰改变了哪个
  名字绑哪个值——那是判断。无人值守地应用它，会把一个**故意**写成这个
  顺序的正确循环改反。编辑器里由作者点选是安全的，`velar fix` 批量应用
  不是。（实施波调研提出，采纳。）

### A3 负数字面量取模

`-7 % 3` 在 Vel（同 JS）是 `-1`，在 Python 是 `2`。

- **触发**：左操作数是**字面量负数**。变量无法静态判断，不触发。
- **消息**：Vel 的 `%` 跟 JavaScript 一致，结果是 `-1`；要 Python 的
  非负取模，写 `((a % b) + b) % b`。

### A4 键控列表的 React 式不可变更新（后补，见 D90 R2 的修订）

D90 R2 裁定 Vel **不为** React 的 `items.map(i => ({...i}))` 兜底：`key` 的身份判定
不放宽，框架不为模型写错买单。那条裁决不变。

但复审时发现它与本裁决的准入门槛冲突：这个写法三条全中——模型一定会写（React 是
它最熟的训练数据）、Vel 静默接受并把整行销毁重建（丢焦点、断输入法组合）、正确写法
`items[index].done = true` 就在旁边。**建议通道不是框架兜底，它是编译器告诉模型它
写错了**，两件事不是一回事。

- **触发**：一个带 `key` 的键控列表，其列表来源是对同一列表的 `map`，且回调返回
  一个**新建的记录字面量**（`{...item, …}` 或逐字段重写）。
- **不触发**：`map` 出的是别的形状（不喂给同一个键控列表）；回调返回原对象；
  列表是新构造的而非同一列表的映射。
- **消息**：这样写会让每一行的身份都变，键控列表会销毁并重建它们——正在输入的
  输入框会失去焦点。原地改字段：`items[index].done = true`。
- **可以带理由抑制**，而且这条尤其需要：列表是 `readonly`、或整份数据来自一次 API
  响应时，`map` + 记录字面量确实是唯一写法。此时作者写下理由即可。

### 同批的文案修正（不是新建议）

以下四处**现在已经是错误**，只是消息指错了路。属于消息修正，不进建议
通道：

| 写法 | 现在的消息 | 应该指向 |
|---|---|---|
| `enumerate(xs)` | Unknown name（无后继） | `for value, index in xs:` |
| `with X as y:` | 讲记录展开 `{...value}` | `using` |
| `raise E(...)` | Unknown declaration keyword | `throw` |
| `def m(self)` | 两条都不含修法 | `self` 是隐式的 |

## 门禁与 AGENTS.md

- `velar check` **打印建议但不因此失败**；汇总行必须点出数量，例如
  `check passed — 3 advisories`，不允许把建议折叠进"通过"里不提。
- CI 与发布**不因建议变红**。让不可抑制的建议阻断发布，等于把它变回
  错误，准入门槛的兜底就失效了。
- 语言服务把建议显示为 warning 级别的波浪线，不是 error。
- `AGENTS.md` 增加一节 **Python / JavaScript 反射对照表**，覆盖本裁决
  首批名册与 charter 已有的同类规则，并明确写入：**留着未处理的建议，
  工作不算完成**——处理的意思是改掉那处写法，或者用带理由的
  `velar-allow` 说明它为什么是对的。这是这一档真正的执行力来源：编译器
  负责发现，AGENTS.md 负责强制，两条腿缺一不可。

## 覆盖要求

- `diagnostic.ts`：新增建议的构造与类型，与 `Diagnostic` 分离。
- `index.ts`：`CompileResult` 增加 `advisories`；第 223 行的总闸不变。
- 词法/语法/分析各自的建议产出点，以及 A2 的机械修复往返覆盖。
- 每条建议都要有**触发**与**不触发**两组用例，误报用例是硬要求。
- 抑制三态各要有用例：带理由的抑制（建议消失、构建通过）、不带理由的
  抑制（**错误**）、过期的抑制（**错误**）。
- 格式化器必须原样保留 `velar-allow` 注释及其理由文本。
- charter 增加一节说明这一档的存在、抑制的拼写与三条规则、以及它永不
  阻止构建。
