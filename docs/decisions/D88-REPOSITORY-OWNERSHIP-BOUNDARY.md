# D88：语言、框架与应用所有权边界

## 结论

目录隔离不等于所有权隔离。只要一个实现仍由 VelarScript 仓库维护、测试和
发布，它就是 VelarScript 的官方能力。将 SQLite、MessagePack、压缩、Noise
或部署厂商实现放进 `adapters/`、`libraries/`、`integrations/`，没有解决
边界问题。

本仓库此后只有一个包层：`packages/*`。其中的包必须直接实现以下至少一项：

1. VelarScript 语言、编译器和目标中立运行时语义；
2. Node、Web、Desktop 官方框架的通用契约与目标原生能力；
3. 构建、检查、测试、语言服务和项目创建所必需的官方工具。

“VelarScript 应用可能会用到”不构成准入理由。数据库模型与驱动、编解码器、
压缩算法、领域算法、云厂商投影、业务组件和通用编辑器组件由实际使用它们的
项目编写或通过 npm 安装，并由该项目维护。

## 框架边界

框架可以提供路由、中间件、生命周期、依赖提供者、HTTP、文件、Worker、
WebSocket、浏览器 DOM 和 IndexedDB 等目标能力。框架只负责组合任意的
应用值，不定义 `Database`、ORM、数据库方言或厂商部署对象。

`velar.entry`、npm 包解析、目标/能力约束、框架扩展协议和 `extern module`
继续属于语言与工具链。它们允许项目拥有自己的包，但不会使这些包成为官方
VelarScript 库。

## 仓库与发布

- 删除 `libraries/`、`adapters/`、`integrations/` 及其生态发布链。
- 已发布的旧包停止维护；注册表采用 deprecated 提示，不执行 unpublish。
- 语言级包解析测试使用测试夹具，不再以真实应用实现充当官方样本。
- 历史记录保留，但当前文档、AI 指南、示例和测试不得继续推荐旧包。
- 现役消费者把所需实现迁入自己的项目，直接拥有底层第三方依赖。

本裁决废止 D87 中“仓库内独立版本生态包”的结论，也收紧 D48 中“从标准库
迁出即可成为本仓普通库”的范围：迁出 Standard 只是第一步；不为语言或官方
框架服务的实现必须迁出仓库。
