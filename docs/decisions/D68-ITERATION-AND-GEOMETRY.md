## 第 176 条 —— `velar test --browser` 增加受控的几何/计算样式读取面

### 用户的框架（比我原来的顾虑更准）

> 通用页面求值逃生通道测试不用那么严格，更多的时候是用的时候的一些约定，
> **因为它不是语言，不需要那么严格。**

**这句话纠正了一个分类错误。** 我原来的顾虑是「开个读取面会变成通用求值通道」——
那是**把语言级纪律套在工具上**。语言要一个拼写一个意思、词汇表封闭、
逃生通道必须带契约；**测试驱动器是工具**，它的边界靠使用约定，不靠语言级封闭。

### 裁决：给它一个真实的读取面

`velar/web-test` 的 `browser` 增加：

| 成员 | 返回 |
|---|---|
| `box(selector)` | 元素盒模型：`x` `y` `width` `height` `top` `right` `bottom` `left` |
| `style(selector, property)` | 该元素**计算后**的单个属性值（文本） |

**只读**，与既有的 `text` / `attribute` / `count` / `visible` 同族。
不开任意 JS 求值 —— 那是另一件事，且真需要时终端一直在那里。

**理由（正面的那一半）**：一个 Web 框架**无法测试「界面有没有排版坏掉」是缺陷**，
而视觉回归恰是浏览器测试最该覆盖的东西。今天 `browser` 有
`text`/`attribute`/`count`/`visible`，**唯独没有任何几何或样式** ——
于是「这个面板塌了」写不出断言。

### 使用约定（是约定，不是门禁）

**断言成因，不断言像素。** 好的断言是「这个元素用了拥有间距的词汇」
或「计算后的 `gap` 是 16px」；坏的断言是「这两个块相距 37 像素」——
后者一改设计就碎，且它测的是渲染引擎不是你的代码。

**写进文档，不做成门禁** —— 按用户的框架，这一层靠约定。

## 第 177 条 —— 用户类型可以声明它被迭代时是什么：`@iterate:`

### 现状：既没设计，也没记进「刻意缺席」

```
export class Bag:
    let items: List<string> = []

for item in bag:        →  VEL4001 Cannot iterate over Bag
```

charter §19 排除的是 **generators / `yield` / `Symbol.asyncIterator` 协议** ——
那是「怎么产出可迭代物」，与「用户类型能否参与 `for x in y`」是两件事。
**今天必须写 `for item in bag.items`，这可能是对的，但它从未被决定，只是缺席。**

**用户裁决：支持。**

### 形态：契约块，与 `@dispose:` 同族

```
export class Bag:
    let items: List<string> = []

    @iterate:
        return items
```

选这个形态的理由：**语言已经有「契约块」这个概念**（`@dispose:`，D45 第 69 条：
它是契约不是方法，不可直接调用）。迭代同样是**语言对这个类型的提问**
而不是作者提供的一个可调用方法，**用同一个形状，零新概念。**

### 它返回语言已经会迭代的东西 —— 不引入迭代协议

`@iterate:` 返回 `List<T>` / `Set<T>` / `Map<K,V>` / `Record<T>` 之一。

**这条是本设计的核心，也是它为什么不违反 §19**：我们**没有**引入迭代器协议、
没有 `next()`、没有生成器。类只是回答「迭代我等于迭代这个」，
而那个东西的迭代语义**语言早就定死了**。

### 边界：反查得出的 8 个消费点，全部成立

我反查了「今天什么东西消费可迭代物」，**不是想出来的**：

| 消费点 | 今天接受 List | `@iterate:` 之后 |
|---|---|---|
| `for x in y` | ✓ | ✓ |
| `for x, i in y` | ✓ | ✓ |
| `for [a, b] in y` | ✓ | ✓ |
| `for k, v in y`（Map/Record） | ✓ | ✓（当 `@iterate:` 返回 Map/Record） |
| `x in y` / `x not in y` | ✓ | ✓ |
| 列表字面量里的 spread `[...y]` | ✓ | ✓ |
| 调用实参里的 spread `f(...y)` | ✓ | ✓ |
| `Set(y)` / `Map(y)` 构造 | ✓ | ✓ |

**一个契约，八个消费点全部跟上** —— 因为它们消费的都是 `@iterate:` 返回的
那个集合，语义与直接写 `bag.items` **逐字相同**。

**让其中任何一个不成立都是陷阱**：`for item in bag` 能写而 `item in bag` 不能，
作者无从理解那条界线在哪。

### `async for` 不在边界内 —— 这是裁决不是缺口

实测 `async for x in values`（List）本来就 **VEL4001**：
`async for` today 只迭代**能力句柄**（`FileWatcher`、`Process`、`eventStream`），
而句柄是 D51 第 113 条**结构判定、只由 web/node 扩展设置**的东西。

**用户类型不做异步可迭代**，理由：一个异步流是**资源**（有生命周期、会失败、
需要 `using`），而资源正是能力句柄在建模的东西。让普通类装作流，
会让「这个东西要不要释放」变得不可判。**记为裁决，不是缺席。**

### 实施要求

1. `@iterate:` 与 `@dispose:` 同一套解析与校验路径；**不可直接调用**（同第 69 条）。
2. 返回类型必须是四种集合之一，否则在契约块处拒绝并教这条规则。
3. **元素类型贯通**：`for item in bag` 里 `item` 的类型是
   `@iterate:` 返回集合的元素类型；`for k, v in bag` 仅当返回 Map/Record 时成立，
   否则拒绝并说明它返回的是什么。
4. 派生类：`@iterate:` 是否继承？**继承**，与普通成员一致 ——
   它不是 `@dispose:` 那种「必须链式」的资源契约，只有一个答案，覆写即替换。
5. 展示补一章或补进第 10 章（类与所有权），**8 个消费点逐个写到**。
6. `readonly Bag` 的迭代：元素按 readonly 投影规则传播，与 `readonly List<T>` 同。
