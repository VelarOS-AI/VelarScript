# D106 — 应用上下文是 Core 静态语义，图与 AI 各自投影（所有者裁决 2026-08-28）

## 问题

VelarScript 是应用层语言。编译器已经知道模块、组件、动作、状态、派生值、
调用、读写和能力边界，但业务名称通常只存在于作者脑中。纯粹按符号绘图会把
技术关系堆在一起；要求作者维护另一份图又会立即与代码漂移。

## 裁决

Core 提供一个可选的上下文标记：

```velar
@context("订单结算")
export def submitOrder(orderId: string) -> string:
    return orderId
```

- `@context` 是 Core 封闭词表中的编译器角色，不是用户定义装饰器，也不是扩展
  注册点。
- 参数只能是一个非空静态字符串，最长 120 个 UTF-16 code units；标记必须紧邻
  一个顶层声明或框架结构项。
- 标记不创建作用域、不包裹调用、不改变求值顺序，也不进入生成的 JavaScript。
- 同一声明最多一个上下文。没有标记时，编译器关系仍然完整，工具可显示为
  “编译器推断”，因此普通代码不承担标注税。
- 框架扩展可以让自己贡献的结构项继承这份 Core 元数据，但不能改变
  `@context` 的语法或运行含义。

## 所有权

- Core 解析并把上下文写入语义符号。
- CLI/LSP 的增量 ownership graph 把上下文随稳定节点 ID、关系、类型和源码位置
  一起传输。
- 编辑器按业务、模块、执行、状态和细节等面向人的层级投影；布局、颜色、折叠
  和导航属于产品展示，不属于语言语义。
- AI 不消费画布坐标。它从同一编译器快照按任务裁剪符号、调用、读写、依赖、
  影响范围和源码证据，以最少上下文获得全局视图。

## 边界

`@context` 只补充作者掌握而编译器无法可靠猜出的业务名称。节点类型、调用、
读写、派生、所有权和能力边界继续由编译器推导；不增加 `@layer`、`@edge`、
`@node` 等绘图指令，也不允许源码控制坐标、颜色或形状。图始终是代码语义的
可更新投影，不是第二份程序。
