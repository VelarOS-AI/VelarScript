# D77 — 泛型类：评估结论与三条待裁决（2026-08-16）

D55 第 120 条把泛型类推到第二增量，并给了一个代价预估。
实施波按要求**先评估再动手**，结论是：**预估两个方向都错，
而且有一条它没列出的硬阻塞。未实施，层一不受影响。**

---

## 第 192 条 —— D55 对泛型类的代价预估作废

| D55 说 | 实测 |
|---|---|
| 静态**贵得多**（要全新变型逻辑） | **比预估便宜。** 若泛型类**不变**，「类可赋值性没有结构成分」这件被算成代价的事，**恰恰让不变性零代码即成立** |
| 运行时**更便宜**，擦除下天然可靠、零校验器工作 | **运行时不是更便宜，是不存在。** `instanceof Stack` 分不出 `Stack<number>` 与 `Stack<string>` |
| —— | **三个未列出的代价，其中一个是硬阻塞** |

### 最重的一条：`Stack<number>()` 在今天的语言里没有拼写

实测五条路全部封死：

```text
identity<string>("x")                  → VEL2031 Type arguments are inferred at each call site
Dog<string>("rex")                     → VEL2031（拒绝消息已经为类措好辞了）
const names: List<string> = empty()    → VEL4001 Cannot assign List<unknown> to List<string>
const box: Box<string> = wrap()        → VEL4001 Cannot assign Box<unknown> to Box<string>
type Pet = Dog; Pet("rex")             → VEL4001 a 'type' declares a shape, not a constructor
```

**记录从不撞上这个，因为记录是字面量、对着绑定的注解检查** ——
`const empty: Stack<number> = {items: []}` 今天就通过。
**类必须被调用，而调用收不到注解。**

D55 第 123 条的「给值就命名它」是**记录的机制**（别名承载 Type 载体），
对类不存在。**所以泛型类会是「可声明、不可构造」。**

### 第二重的一条：`is Stack<number>` 会静默接受一个不健全的收窄

```text
is T             → VEL4022 Type parameter 'T' is erased at runtime
is Box<T>        → VEL4022 同上
is Box<string>   → 接受，且真的逐字段检查（记录靠单态化做到）
is Dog           → 接受，instanceof
```

`Stack<number>` 里没有 `parameter` 种类，
所以 `rejectErasedRuntimeCheck` **不触发**，它会被默默接受 ——
**而类无法单态化**（状态可能 private、可能为空、可能在 getter 后面）。

**这正是 D55 第 126 条自己用来否决裸 `Box` 的那条论证，在这里力度更大**：
泛型类的 `is` 是**构造上**接受一切。

### 实施波报出的两处 D55 与代码不符

1. **第 120 条说「类方法把 `T` 放在逆变位置——今天全仓没有任何东西建模过」。**
   **逆变机制存在且每天在跑**（`types.ts:1318` 是标准逆变，记录的函数型字段
   今天就享有它）。缺的不是逆变，是**类成员没有任何结构比较路径** ——
   而在不变方案下它永远不需要被走到。**这句话高估了代价。**
2. **第 120 条说运行时「零校验器工作」** —— 那是唯一一处会**引入不健全**的判断。

## 第 193 条 —— 三条待裁决，泛型类在它们定案前不实施

### 一、泛型类是否不变？

**实施波建议「是」，我同意。** 健全、零变型代码、与 Java/C#/Kotlin 默认一致；
类有方法，协变本来就不健全（D55 自己也这么说）。

**代价要写进 charter**：它与第 122 条给记录立的「只读协变」是**两条不同的规则**，
不写明会读起来像不一致。

### 二、`is Stack<number>` 怎么办？

**建议拒绝**，复用 VEL4022 的措辞族（「类型实参在运行时被擦除；检查 `Stack` 本身」）
—— 与第 126 条拒绝裸 `Box` 同一条论证。
另一个选项是默默接受一个不健全的收窄，**不建议**。

### 三、`Stack<number>()` 的拼写 —— **这条没有便宜答案**

三个选项，每个都是新裁决：

| 选项 | 代价 |
|---|---|
| 新的表达式位语法（`Stack<number>()`） | 第 123 条**正是以同样的文法理由**替记录否决过它 |
| **让注解流进泛型调用点推断** | 改的是 `def` 的泛型推断，波及面大于类；**但顺带修好 `const names: List<string> = empty()` 这个今天就别扭的情形** |
| 让 `type` 别名承载构造器 | 给 `type` 一个新含义 |

**实施波倾向第二个，我也倾向它** —— 因为它修的不只是泛型类，
是一条今天就存在的摩擦。**但那是对 `def` 泛型推断的改动，要你先认。**

**这条必须先定**，否则泛型类可声明不可构造。

## 可以确认白拿的（供将来的实施波直接用）

- 解析：`parseTypeParameters` 九个站点已读 `<T: Bound>`；那条 VEL2025 只是拿掉
- **约束完全白拿**：`collectTypeArgumentBoundViolations` 与声明形式无关，
  `class Stack<T: Bound>` 原样可用；4×3 授予表同理
- `substituteTypeParameters`、`genericApplicationIdentity`/`Type`、`mapClassInfo`
- VEL2031 的拒绝消息已经会说 `write 'Dog(...)'`
- 方法自带 `<T>` 今天就合法，与类级 `<T>` 不冲突
- 类永远进不了 `readonly` 深数据，所以第 122 条与泛型类无交集

**机械工作量约为记录那半的 0.8 倍。问题从来不在量，
在于它被三个没有回答的语义裁决卡住。**

## 第 194 条 —— 三条定案（2026-08-16）

| | 裁决 | 谁定的 |
|---|---|---|
| 泛型类是否不变 | **不变** | 我的建议，所有者未反对 |
| `is Stack<number>` | **拒绝**，复用 VEL4022 措辞族 | 我的建议，所有者未反对 |
| **`Stack<number>()` 的拼写** | **让注解流进泛型调用点推断** | **所有者裁决** |

**前两条如实标注为「我的建议」** —— 所有者只对第三条明确表态。
若将来复核，第三条是他的取舍，前两条是我的推理，可以被推翻而不必推翻他的判断。

### 第三条的真实含义与它的顺序后果

它不是"给泛型类加个拼写"，它是**给泛型调用引入上下文类型**：

```text
今天   const names: List<string> = empty()
       → VEL4001 Cannot assign List<unknown> to List<string>

之后   注解成为调用点的期望类型，T 解为 string
```

**所以它修的不只是泛型类** —— 所有者选它正是因为这一点。
但**它比泛型类本身更大**，顺序因此是：

> **上下文泛型推断 → 然后才是泛型类**

反过来做不成：没有前者，泛型类可声明不可构造。

### 实施者要调查并上报的（不要自行裁决）

**期望类型传播到多远?** 这是本条唯一没被回答的问题，
而它决定改动的波及面：

| 位置 | 要不要传播 |
|---|---|
| 带注解的绑定 `const x: List<string> = empty()` | 显然要 —— 这是本条的出发点 |
| 实参位 `f(empty())` where `f(x: List<string>)` | ? |
| 返回位 `def g() -> List<string>: return empty()` | ? |
| 记录字段位、JSX 属性位 | ? |

**注意 D51 第 108 条已经为 JSX 属性位的空列表做过同一件事**
（「把已有的上下文推断补到一个漏掉的位置」）——
所以这条不是全新机制，是**把它推广到泛型调用**。
**先去查那条今天覆盖了哪些位置**，再决定泛型版本对齐到哪。

**已知风险，要一并评估**：读注解的推断会让错误**更晚、更难懂**
（TypeScript 有这个问题）。若某个位置的传播会让诊断变差，
**报出来，宁可那个位置不传播**。
