# VelarScript 0.1 Acceptance Matrix

Status: Core, Velar Compiler, the first production Web platform, and injected
Workbench support are accepted for the production-hardening/library stage.

This document maps the language charter to durable evidence. A green typecheck
alone is not acceptance: every row must have either an automated contract or an
explicit browser/editor smoke gate.

## Language and runtime surface

| Contract | Evidence |
| --- | --- |
| `const`/`let`, initialized bindings, immutable parameters, block scope | Compiler analyzer and `compiles bindings, functions, and strict equality`, `rejects reassignment of const bindings` |
| Python-style block `if`/`else`/`for`/`while`; JavaScript-order `? :` only for inline conditions | Parser, formatter, `examples/foundation.vel`, `examples/core.vel` |
| `none` is the only ordinary empty value; optional JS results normalize at the boundary | `lowers none and readable logical operators`, `normalizes optional members and calls to none` |
| No `var`, `null`, `undefined`, dynamic `this`, `new`, prototype manipulation, `eval`, `with`, `arguments`, `===`, or `!==`; discarded `schema`/source `effect`/`onMounted` spellings stay unavailable | `rejects legacy and discarded design surface with intentional diagnostics` (`VEL1005`) |
| Boolean-only logical operators and strict conditions | Analyzer condition checks and `compiles the Core language contract` |
| Strict `==`/`!=`, explicit string conversion, JavaScript value/reference behavior | `compiles bindings, functions, and strict equality`, `safe JavaScript imports use explicit extern declarations` |
| `List<T>` and `Map<K, V>` annotations with natural `Map()` construction | `collection operations use Velar return and bounds semantics`, `supports reduce callbacks, map key iteration, and friendly core builtins` |
| One `type` declaration for static help and runtime validation; no `schema` | `checks runtime type declarations and optional access`, `runtime data validation composes nested data types and class identity` |
| Classes call without source-level `new`, use explicit `self`, retain methods as callbacks, and expose no inheritance/prototype API | `compiles the Core language contract`, `nested method closures capture self without dynamic this` |
| Safe JS imports require declarations; unsafe values cross an explicit boundary | `safe JavaScript imports use explicit extern declarations`, `validates annotations and keeps any behind unsafe boundaries` |

| Contract | Evidence |
| --- | --- |
| Fresh lexer → parser → AST → analysis → Web lowering → ESM/source-map pipeline | `npm run check`, compiler architecture, compiler tests |
| Stable `VEL1xxx`–`VEL5xxx` diagnostics | Diagnostic assertions across the compiler suite; codes are transported unchanged through LSP and Workbench |
| Multi-file `.vel` graph, exported reactive interfaces, and interface-aware checking | `CLI checks and builds a multi-module project`, reactive module import tests, imported signature tests |

| Versioned language server with diagnostics, completion, hover, and formatting | `language server publishes diagnostics, hover, and completion`; Workbench protocol contract test |

## Velar Web

| Contract | Evidence |
| --- | --- |
| Native JSX fragments and declared children lower to owned DOM without React or a virtual DOM | JSX fragment/children test and component DOM test |
| Module/component `state`, lazy `computed`, explicit `watch`, `mounted`, and sibling `cleanup` | Reactive module/import tests plus generated runtime ownership/scheduling invariants |
| DOM jobs precede watch jobs; `tick()` observes the committed DOM | Generated runtime queue contract and browser smoke gate |
| Keyed dynamic lists reuse scopes and reject missing/duplicate keys | `requires and lowers stable keys for dynamic JSX lists` and Todo browser smoke |
| Writable string/number/checked bindings, event modifiers, refs, class/style directives, opt-in unsafe HTML | JSX/forms test, Web directive test, and browser smoke |
| Scoped CSS by default, explicit global CSS, extracted production CSS | Component compiler test and `CLI emits complete Web application assets` |
| Todo and API Dashboard acceptance applications | `examples/todo`, `examples/api-dashboard`; build and browser smoke gates |
| Fetch, async functions, runtime parsing, npm ESM interop, public assets | API Dashboard build/browser smoke and npm bridge assertions |
| Explicit routing, HTTP, persistence, and tests | Configured project standard-module test and `examples/production-web` |
| Minified/tree-shaken bundles, hashed assets, splitting-ready ESM, and linked maps | Production Web asset test and esbuild metafile output |

## Native Workbench support

| Contract | Evidence |
| --- | --- |
| `.vel` support is a default injected Workbench contribution, not a downloaded grammar or a core hard-code | Workbench host isolation and contribution registry/tokenizer/project-command tests |
| Velar diagnostics, completion, hover, formatting, and protocol version 1 | Shared stdio LSP test and real Velar language-server smoke |
| Python syntax and Workbench-owned Pyright runtime | Real Pyright startup, diagnostic, and hover test |
| JavaScript/TypeScript and related Web formats keep their built-in services | Workbench full check and focused registry test |
| Java, C/C++, Go, and Rust have no language-service/plugin surface | Focused registry test; unknown extensions resolve as plain text |
| Language-server failures explain the missing toolchain; string codes such as `VEL5016` survive the editor boundary | Missing-server and string-code LSP contracts |

## Release gate

Run before declaring the milestone green:

```text
VelarScript: npm run check && npm test
Workbench:   bun run check
Workbench:   bun run package:app:dir && bun run verify:app:dir
Browser:     build and open Todo + API Dashboard; exercise form updates,
             keyed lists, scoped CSS, Fetch/npm data, and dev-server HMR
Editor:      open .vel and .py projects; verify diagnostics, completion, hover,
             Velar formatting, protocol mismatch handling, and restart cleanup
```

## Next big stage

The next stage is production hardening and the reusable Web ecosystem: richer
navigation/refactoring, browser debugging, library distribution, performance
budgets, larger application validation, and API stabilization. Language,
compiler, Web lowering, and Workbench support continue as one delivery axis.
`velar/game` remains deferred and must not redefine Core or Velar Web.
