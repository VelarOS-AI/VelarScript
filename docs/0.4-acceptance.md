# VelarScript 0.4 Acceptance Matrix

Status: distribution and broader Web-application milestone complete

## Distribution and projects

| Contract | Evidence |
| --- | --- |
| Compiler and CLI publish JavaScript plus `.d.ts`, require Node 24, and remain independent from Workbench | Package manifests and build tsconfigs |
| Packed tarballs install and run in a clean consumer | `npm run test:packages`: installed CLI version/build and compiler API probe |
| CLI/compiler versions are exact and package contents exclude repository tests | Tarball contract assertions |
| `velar create` refuses non-empty targets and creates a usable versioned project | Project lifecycle integration test |
| Legacy manifests upgrade explicitly; future versions fail closed | `velar upgrade --check`, write upgrade, and formatVersion 99 rejection |

## JavaScript ecosystem boundary

| Contract | Evidence |
| --- | --- |
| Safe npm imports consume a deliberately limited `.d.ts` subset | Declaration parser and installed typed-package project test |
| Generics and other unsupported constructs remain unknown with non-blocking `VEL9002` notices | Generic identity declaration assertion and LSP notice transport |
| Explicit `extern module` remains authoritative and unsafe imports remain explicit | Existing safe/unsafe JavaScript boundary tests |
| JavaScript package `.js`, `.d.ts`, and manifest changes participate in development invalidation | External typed JavaScript package watcher test |

## Web platform and browsers

| Contract | Evidence |
| --- | --- |
| Web API version 0.4 adds `Head`, announcements, redirects, and form values/errors without a framework runtime | Versioned standard-module contract test |
| Form errors set and clear aria-invalid/describedby and use alert semantics | Chromium/Firefox/WebKit form acceptance |
| Page title and description follow route ownership and cleanup | Three-engine route/head acceptance |
| Empty buttons, anchors without href, and unsafe blank targets are diagnosed | VEL5026-5028 accessibility tests |
| Chromium, Firefox, and WebKit execute the same reactive, routing, form, Head, npm, and deep-refresh flow | Playwright browser matrix |
| Production manifest records both Velar and JavaScript dependency identities | Manifest dependency summary test |

## Workbench seam

| Contract | Evidence |
| --- | --- |
| Workbench remains generic and consumes LSP protocol v1 | Product-boundary and language-support tests |
| Versioned project upgrade check is injected as generic command metadata | Workbench Velar contribution test |
| Installed toolchain is resolved project-locally | Workbench language-service descriptor and package-consumer gate |

## Acceptance commands

```text
Velar:       npm run check && npm test
Packages:    npm run test:packages
Browsers:    npm run test:browser
Example:     velar check/test/build examples/production-web
Workbench:   bun run check
Packaging:   bun run package:app:dir && bun run verify:app:dir
```

## Next big stage

Velar 0.5 is the pre-release productization stage: release provenance and npm
publication rehearsal, CI browser/platform matrices, a larger real Web
application, static-host deployment contracts, security/CSP hardening, and
installed-tarball Workbench end-to-end validation. Actual registry publication
remains an explicit release action. SSR/server, a custom registry, a custom
debug protocol, complex type-level programming, and `velar/game` remain
deferred.
