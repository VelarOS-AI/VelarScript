# VelarScript 0.7 Acceptance Matrix

Status: internal 0.7A–0.7G engineering gate complete; external preview remains

## 0.7A error control flow

| Contract | Evidence |
| --- | --- |
| Source code can deliberately fail without exposing arbitrary JavaScript throws | `throw` accepts only `Error` instances and nominal subclasses; strings, numbers, objects, optionals, and `unknown` are rejected |
| Error subclasses keep native JavaScript identity | A thrown `ValidationError` remains `instanceof ValidationError` after `catch` and exposes its inherited message |
| Foreign JavaScript failures do not break the catch-binding type contract | A non-Error unsafe JavaScript throw is wrapped as `Error`, preserves the raw value as `cause`, and executes in Node acceptance |
| Async failures use the same language semantics | An async function whose terminating path throws satisfies return analysis and is handled through `await` plus `catch` |
| Cleanup cannot be skipped silently | `finally` runs after a handled Velar error in runtime acceptance |
| Thrown paths are terminal for static return analysis | A typed function with exhaustive return-or-throw branches passes; incomplete returning functions still fail |
| Remainder is available without importing JavaScript arithmetic | `%` and `%=` compile and execute with JavaScript remainder semantics; non-number operands fail checking |
| Parser failures are intentional | Bare `throw` reports `VEL2009` instead of producing malformed JavaScript |
| Editor behavior follows compiler ownership | `throw` is exposed through `velar lsp`; semantic indexing visits thrown expressions and Workbench consumes the installed LSP unchanged |

## 0.7B application resilience, configuration, and logging

| Contract | Evidence |
| --- | --- |
| Applications own one typed error channel | `velar/app` exposes `onError` and `reportError`; reports normalize `Error` and record phase, detail, component, and timestamp |
| Initial failures never become an unexplained blank page | Root mount is evaluated lazily and a failed initial render produces an accessible compiler-owned `role=alert` fatal state |
| A failed reactive render preserves usable output | Dynamic and keyed updates create the replacement transactionally; the browser matrix proves the prior DOM remains after a deliberate render failure |
| Event and lifecycle rejection are handled consistently | Sync throws and rejected event promises plus async `mounted` work report through the same channel without an unhandled browser failure |
| Cleanup is failure tolerant | Independent cleanup steps are guarded individually, later steps still execute, and browser acceptance observes their persisted continuation marker |
| Public configuration is explicit and typed | Only `velar.json.web.publicConfig` is embedded; `publicConfig(Type)` validates it with the existing `type` declaration and returns recursively frozen data |
| Public input cannot become an implicit secret loader | Config rejects non-object/non-JSON input, dangerous prototype keys, and values beyond 64 KiB; `.env` and `process.env` are never read |
| Source logging is structured and owned | Standard API 0.3 adds scoped leveled loggers, immutable records, redirectable sinks, explicit sink cleanup, internal sink-failure fallback, and no telemetry or source `console` |
| Real Web behavior is cross-browser | Release Studio exercises config, logs, async event failure, failed render retention, mounted work, and cleanup continuation in Chromium, Firefox, and WebKit for development and CSP production |
| Editor behavior stays injected | The installed-toolchain Workbench gate requests `velar/app`, `velar/config`, and `velar/log` completion through the generic project-local LSP host |

## 0.7C project testing, deployment, extension boundary, and soak

| Contract | Evidence |
| --- | --- |
| Browser tests belong to projects | `.browser.test.vel` and `velar test --browser` are product contracts; Core discovery excludes browser files and generated projects include a passing browser test/script |
| Automation stays small and typed | `velar/web-test.browser` exposes only navigation, interaction, observation, waiting, path, and viewport methods; raw DOM/Playwright evaluation is not exposed |
| Tests exercise production reality | The CLI builds an isolated CSP production site, serves the deployment contract, creates a fresh context per test, and fails page/console runtime errors automatically |
| The browser matrix is selectable | Chromium is the local default and explicit Chromium, Firefox, WebKit, and `all` modes pass Release Studio recovery and eight-cycle route/cleanup soak scenarios (6/6 project flows) |
| Packed CLI carries the feature | A clean consumer installs packed compiler/Web/creator/CLI tarballs, creates a project, and passes its generated browser test in real Chromium |
| One real host adapter exists | Root-base `adapter: "netlify"` translates manifest headers and SPA fallback to official `_headers` and `_redirects`; non-root base fails closed |
| Adapter output is release identity | Provider files are compiler-reserved, receive `adapter` asset roles, sizes and SHA-256 values, and participate in `buildId` |
| The clean break is explicit | Generated projects use format 2 and declare `@velarscript/web`; missing, format-1, and unknown future manifests fail closed without a compatibility loader or rewrite command |
| Workbench remains a generic host | Only the injected Velar contribution adds Browser Test command metadata; the shared editor/project-command host remains free of Velar branches |

## 0.7D verified production artifacts

| Contract | Evidence |
| --- | --- |
| Build hashes are user-verifiable | `velar verify` resolves a project/build directory and checks exact file-set equality, regular files, normalized unique paths, byte sizes, SHA-256 values, deterministic order, and recomputed `buildId` |
| Manifest relationships are verified | Entry, stylesheet, deployment, fallback, CSP, caching, compiler/API identity, and adapter files must have the correct declared roles and matching cross-manifest values |
| Tampering fails closed | Acceptance rejects an undeclared file, a symbolic link, and a modified hashed entry; missing/invalid production output produces an actionable failure |
| Preview cannot accidentally serve stale output | `velar preview` invokes the verifier before binding a port and prints the verified build identity |
| Preview matches deployment semantics | Root/deep navigation, base routing, CSP, no-cache documents, GET/HEAD, 405 method refusal, and missing-asset 404 are executable acceptance contracts |
| Product tests use the same server | `.browser.test.vel` builds are verified and run through the production preview implementation rather than a separate repository static server |
| Packed projects retain the loop | Installed tarball acceptance creates, builds, verifies, and browser-tests a generated project |
| Editor stays injected | Workbench adds Verify Production Build and Production Preview only as Velar contribution command metadata |

## 0.7E reproducible and disclosure-safe builds

| Contract | Evidence |
| --- | --- |
| Output location cannot change release identity | Production modules are loaded from stable real `.vel` paths with inline compiler maps rather than a random temporary `.js` tree |
| Repeated builds are byte reproducible | Two builds of the same project into different output directories have deeply equal manifests and byte-identical declared assets |
| Source mapping survives the stable pipeline | Explicitly enabled maps still point to Velar application/package sources and include their source content |
| Source disclosure is intentional | `web.build.sourceMaps` is a validated boolean, defaults to `false`, and is written to the production manifest |
| Generated projects use the safe default | `velar create` writes `sourceMaps: false`; a default single-file production build contains no linked map or source-map asset |
| Opt-in maps remain verified | Release Studio and reproducibility acceptance explicitly enable maps, which remain hashed and checked by `velar verify` |

## 0.7F hosted deployment verification

| Contract | Evidence |
| --- | --- |
| Local correctness is not mistaken for hosted correctness | `velar verify-deployment` always runs the format-2 local verifier before contacting the supplied origin |
| A provider cannot silently alter a release | Every public build file plus `velar-build.json` is fetched without redirects and checked by decoded byte size and SHA-256; adapter-control files are excluded because the provider consumes rather than serves them |
| MIME and policy survive the host | Known file types, every applicable manifest security/cache header, root document caching, and SPA document caching are checked against real responses |
| SPA routing cannot hide asset loss | The root and a unique deep navigation must serve the exact `index.html`; a unique missing `/assets/*.js` request must remain HTTP 404 |
| Targets are safe and reproducible | Public targets require an origin-only HTTPS URL, credentials/query/fragment/path are rejected, cache-busting uses the build identity, and only loopback hosts may use HTTP |
| Failure modes are executable | Acceptance rejects changed bytes, wrong immutable caching, a 302 access redirect, an asset rewritten to HTML, an insecure public target, and a target with an undeclared path |
| Root and subpath contracts work | The same verifier passes a root Netlify-shaped build and a neutral `/demo/` build through the product preview server |
| Editor remains injected | Workbench adds Verify Deployed Site only through the Velar contribution; the generic editor host and compiler remain independent |

## 0.7G external-preview evidence

| Contract | Evidence |
| --- | --- |
| Automation receives structured evidence | `verify-deployment --json` emits a format-version-1 report with timestamp, target, base, compiler/API identity, source-map policy, `buildId`, and file/route/header counts |
| A report cannot mix build identities | Report creation rejects a deployment result whose `buildId` differs from the locally verified build |
| CI binds observation to source | The manual external-preview workflow rebuilds Release Studio from the checked-out revision and attests the report plus exact build/deployment manifests with `actions/attest@v4` |
| Verification cannot become implicit deployment | Workflow acceptance rejects Netlify deployment, npm publication, and secret access; the only external input is an explicit HTTPS origin |
| Evidence remains retrievable | The report and manifests are uploaded as a SHA-named workflow artifact after JSON parsing and attestation succeed |
| The hosted candidate is reproducible | `preview:prepare` builds the checked-in root Netlify profile twice into distinct directories and proves deeply equal manifests plus byte-identical declared assets |
| Preparation cannot erase arbitrary data | The command replaces only an absent path or a directory containing a Velar Web build manifest; an unrelated directory and its sentinel file survive refusal |
| Deployment metadata follows the profile | Typed `publicConfig` supplies canonical/social URLs for `/app/` and root profiles; the social SVG is a declared hashed asset |
| The exact candidate executes | Chromium opens the prepared root bundle with CSP, validates metadata/share asset/root and deep routes/reload, observes missing-asset 404, and reports no page or console failure |

## API and format versions

The current `0.9.0-dev` toolchain retains Standard API `0.4`, Web API `0.7`,
build manifest format `2`, and LSP protocol `1`. Project format `2` is a clean
break with explicit extensions; no legacy loader or migration command remains,
and the generic Workbench host protocol is unchanged.

## Remaining production gate

0.7 is not yet production-complete. The authoritative remaining requirements
are tracked in [production-readiness.md](production-readiness.md). In particular,
external preview use, a stable clean tagged source, a publishable license
decision, public release authority, and release-candidate audit remain unproven.
