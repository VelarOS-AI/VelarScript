# VelarScript runtime and JavaScript boundary ledger

Status: required current architecture ledger

This document classifies how observable VelarScript semantics cross the generated
JavaScript and host-runtime boundary. It does not define a second language. The
[language charter](../language-charter.md) remains the authority for source-level and
user-observable behavior. If this ledger, an implementation note, or a test
conflicts with the charter, the charter wins and the other artifact must change.

The [compiler architecture](compiler-architecture.md) owns implementation and
package responsibility. Tests prove the charter and this mapping; they do not
create new semantics.

## Boundary classes

| Class | Name | Meaning |
| --- | --- | --- |
| H | Host-inherited | The charter deliberately retains JavaScript representation or runtime behavior. |
| E | Compile-erased | The construct is checked or used for tooling, then has no independent runtime representation. |
| L | Compiler-lowered | The emitter rewrites the construct to preserve VelarScript evaluation and safety rules. |
| R | Runtime-controlled | Generated code calls a compiler- or extension-owned runtime contract. |
| C | Checked foreign ABI | A trusted declaration is checked statically; it is not an implicit runtime schema or sandbox. |
| U | Explicit unsafe | Source spelling opts out of checked guarantees, and the caller owns the risk. |

Classes apply to operations, not whole types. A record uses host object identity
(`H`), compiler-controlled construction (`L`), runtime validation (`R`), and a
checked or unsafe foreign boundary (`C` or `U`) depending on how it entered the
program. Collapsing those operations into one label would hide the boundary.

## Runtime ABI authority

`packages/compiler/src/runtime-abi.ts` owns three independent identities:

- `VELAR_RUNTIME_REGISTRY_KEY` identifies the one global registry slot shared by
  generated Core helpers and optional runtime-providing extensions. Change the
  key only when two runtime generations must never share a registry value.
- `VELAR_RUNTIME_SCHEMA_VERSION` identifies the shape and semantics consumed by
  generated code. Change it when a required field or an observable field contract
  changes. It is intentionally independent from the language and npm package
  versions.
- `VELAR_TYPE_REGISTRY_KEY` identifies the separate registry of compiler-known
  runtime `Type` objects shared by Core and every extension, including targets
  with no reactive runtime. Its global descriptor is immutable and validated;
  registration uses the captured WeakSet intrinsic rather than an overridable
  instance method.

`packages/web` owns the browser implementation of the current schema. It must
validate an existing registry descriptor, schema version, field set, collection
brands, and callable fields before reuse. Required Web consumers fail closed on
an incompatible registry. Opportunistic Core adapters may ignore an absent or
incompatible optional runtime capability and retain ordinary Core behavior.

Compiler extensions that consume or implement either registry import all
identities from `@velarscript/compiler/extension`; they do not repeat string
literals. Exact package pins reduce accidental mixing, while runtime validation
protects generated modules that are nevertheless combined outside the package
manager's graph.

Pins alone do not settle the compiler generation. The CLI resolves a compiler
extension from the project before the toolchain, deliberately, so a project that
declares its own copy of an official target extension routes around the CLI's
pin entirely and brings that release's nested `@velarscript/compiler` with it;
neither `protocolVersion`, which has never moved, nor `apiVersion`, which is
compared against the extension's own manifest, can see the difference. The npm
versions are the one generation marker both halves carry, so
`resolveExtensionPackages` compares every project-resolved extension's version
against the version this CLI was published against and refuses a mismatch,
naming both packages and both versions. An extension this CLI does not pin, an
extension resolved from the toolchain or the bundled registry, and a toolchain
whose own manifest is unreadable are not refused: a CLI that cannot state its
generation must not reject the project's. The official `create-velar` templates
install every `@velarscript/*` dependency at an exact version rather than a
caret range, so an ordinary install cannot pair a newer target extension with
the pinned CLI. The one range they write is a component package's
`peerDependencies` entry, which installs nothing and only states which target a
consumer must already have.

For B-NODE-HOST and B-DESKTOP-CAPABILITIES, process completion now has two
deliberately different recovery modes. Explicit `stop()` retains an
unconfirmed handle and remains retryable. Natural root exit instead owns a
bounded output-drain phase: the isolated host terminates the original process
group, escalates after two seconds, and after five seconds closes only its own
stdout/stderr read ends with a terminal error if an escaped descendant still
holds the pipes. This bounds `next()`/`wait()`/`run()` without pretending that
an exact executable grant is an OS sandbox. Desktop transports terminal stop
errors as the same validated result/error envelope as Node.

`wait()` and `run()` preserve that ownership rule rather than treating every
Promise rejection as a terminal child result. The private Node/Desktop host
protocol returns a validated result/error/retained outcome: terminal outcomes
release and remain idempotently cached, while unconfirmed termination retains
the handle and clears only the rejected in-flight wait. Raw bridge rejection is
also retryable because it cannot prove resource release. A wait following a
retained outcome reissues forced termination. Concurrent waits
coalesce, while a confirmed Stop outcome supersedes a stale concurrent wait
cache before the handle is released. Since `run()` does not expose its temporary Process value, the shared
runtime retains it after a non-terminal failure and retries stop confirmation
in the background. Timeout and output-bound termination wake an already active
wait and start their own five-second confirmation window, so missing
`exit`/`close` cannot turn an execution deadline into an unbounded wait.

## Required feature decision record

Every new public language, standard-module, Web, Node, Desktop, or JavaScript-bridge
feature must answer these questions before implementation:

1. What JavaScript or host representation carries the value?
2. Which host behaviors are deliberately inherited?
3. Which host behaviors are rejected, normalized, or replaced?
4. Which boundary classes apply to each operation?
5. What can the analyzer prove, and what still requires runtime validation?
6. What is the exact evaluation order and evaluation count?
7. What adaptation occurs when values enter and leave foreign code?
8. What fails at compile time, module initialization, or ordinary runtime?
9. Does the feature consume or change a cross-module ABI?
10. Which diagnostic, emitted-code, and execution tests prove the contract?

A proposal is not implementation-ready while any answer is unknown. Product
semantics belong in the charter first; implementation choices belong in the
architecture and code only after that contract is fixed.

## Verification gate

Boundary work is complete only when all relevant layers are present:

1. A charter statement defines the user-observable behavior.
2. This ledger classifies the operation and names its owner.
3. A diagnostic test proves rejected source behavior.
4. An emitted-code test proves lowering, ABI use, and single evaluation where relevant.
5. An execution test probes hostile host values such as accessors, sparse arrays,
   poisoned prototypes, fake thenables, cross-realm values, incompatible runtime
   registries, and JavaScript `undefined`.

Purely host-inherited or compile-erased rows may not need all five layers, but the
ledger must make that omission explicit rather than leaving it accidental.

One gate runs at a time per checkout. A gate rebuilds `packages/*/dist` through
a clean step, binds fixed test ports, and writes `.velar/` sandboxes inside
`examples/`; that state belongs to the checkout rather than to the run, so two
gates started in one working tree corrupt each other and the failure stops being
about the code. The workspace scripts that start one — `build:packages`,
`check`, `test`, `test:browser`, `test:packages`, and `velar` — therefore run
under `scripts/gate-lock.mjs`, which holds `<checkout>/.velar/gate.lock` for the
duration; a later gate waits for it instead of starting. A recorded holder is
reclaimed only when it names this host and its process is gone, so a running
gate is never displaced. A lock file whose contents do not parse as a holder
record was abandoned between creation and its first write: it names no host and
no process to test, so it is reclaimed on age alone, ten seconds after its last
modification. Individual checks invoked directly, such as `check:docs`, take no
lock. The lock is re-entrant within one process tree, so a locked gate may call
another locked script, and it lives inside the workspace it guards, so separate
checkouts, git worktrees, CI jobs, and the temporary workspace built by
`scripts/isolated-toolchain-build.mjs` never wait on each other. It is
deliberately not in the system temporary directory: that directory is
world-writable on a shared host and a path derived from the checkout is not a
secret, so any local user could pre-create the lock naming a process that never
exits and wedge every gate in the checkout for good. `.velar/` is already
ignored by git and already the CLI's own scratch namespace, so the lock never
dirties the tree a release candidate checks.
