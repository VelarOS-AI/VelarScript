# VelarScript 0.8 Acceptance Matrix

Status: 0.8A–0.8F internal gates implemented; no publication or external deployment

## 0.8A checked dynamic modules and lazy Web components

| Contract | Evidence |
| --- | --- |
| Dynamic loading remains statically knowable | Only a literal relative path ending in `.vel` is accepted; variables, bare packages, `.js` files, and malformed paths produce compiler diagnostics |
| The type system crosses the asynchronous boundary | `import("./page.vel")` is a `Promise` of the target module export object; missing exports, wrong function arguments, non-component lazy exports, and wrong JSX props fail checking |
| One dependency graph remains authoritative | Dynamic edges participate in source-root confinement, complete project loading, reverse-dependent invalidation, module counts, and project failures |
| Reactive ownership stays explicit | A dynamically loaded module with exported top-level `state` or `computed` is rejected; lazy modules expose functions, classes, types, or components instead |
| JavaScript interop does not become ambient | Dynamic JavaScript loading is absent; checked or unsafe JavaScript remains behind the existing explicit static `import js` forms |
| Development output remains native ESM | `.vel` dynamic paths lower to `.js` `import()` edges that the development server can serve without a second runtime loader |
| Production code splitting is real and verifiable | A two-module Web application emits a hashed entry and a separate hashed lazy chunk; the chunk is part of format-2 inventory and passes `velar verify` |
| Lazy routing owns all intermediate states | `velar/web.lazy` renders an optional loading component, caches successful resolution, retries failures, reports the `resource` error phase, renders a supplied or accessible default failure state, and destroys the prior child before replacement |
| Props stay typed | `lazy` returns the selected component constructor type, so JSX keeps the dynamically loaded component's original required and optional prop contract |
| The real application uses the feature | Release Studio loads its About route as a separate module and passes repeated route navigation and cleanup in the product browser-test command |
| Editor navigation remains compiler-owned | The semantic index records static and dynamic module path spans; the generic LSP definition operation opens the target `.vel` source without a Workbench-specific resolver |
| Incremental editing remains bounded | Changing a dynamic target recompiles the target and its reverse importer while reusing an unrelated module |

## 0.8B strict block matching

| Contract | Evidence |
| --- | --- |
| Branch syntax stays readable | `match value:` contains indented `case` blocks and an optional `else`; there is no inline match expression or brace/fallthrough syntax |
| Equality remains one language rule | String, number, boolean, and `none` cases use strict JavaScript identity/value equality, matching Velar `==`; the subject is evaluated once |
| Related values stay compact | One case may group multiple comma-separated literals without duplicating a body |
| Every branch owns its bindings | Emission wraps each case in its own lexical block, so the same `const` name may be used safely in different cases |
| Invalid matches fail before JavaScript | Duplicate literals, cross-type cases, computed case expressions, a case after else, duplicate else, empty case, empty match, and orphan case produce stable parser/type diagnostics |
| There is no implicit fallthrough | The compiler emits an internal break after every non-terminating case; source `break` remains a loop-only statement |
| Return analysis understands the construct | A match with `else` satisfies a typed function only when every case and else path returns or throws; a partial match remains incomplete |
| Reactive Web code uses the same construct | Match subjects inside components lower through reactive reads, and Release Studio uses match in its real project-status rendering path |
| Editor support stays injected | `match` and `case` are compiler/LSP keywords and are highlighted only by the injected Workbench Velar contribution; the generic host is unchanged |

## 0.8C safe multipart uploads

| Contract | Evidence |
| --- | --- |
| Upload construction is explicit | `formBody()` returns a typed builder with text field, single/multiple file, removal, membership, and field-name operations |
| File authority cannot be forged structurally | The public record remains frozen metadata; the native `File` is held in a host-private shared WeakMap registry, and runtime attachment rejects ordinary lookalike objects |
| Browser globals remain wrapped | Velar source receives neither `File`, `FormData`, `Blob`, `Headers`, nor the private symbol; unsafe JavaScript remains the only escape hatch |
| Multipart headers stay valid | The browser generates the boundary and a source-supplied `content-type` with a form body fails rather than sending a mismatched header |
| Existing HTTP ownership still applies | Form bodies use the same lazy request, timeout, cancellation, error normalization, response readers, and runtime `type` parsing path |
| Static typing catches common misuse | Field values must be strings, file methods require the exact picked-file metadata shape, and file lists retain their inferred element contract |
| The real Web application exercises the bridge | Release Studio selects and reads a file, attaches it with a text field, posts it, parses a typed response, and exposes the result in browser acceptance |
| Cross-browser transport is verified | Chromium, Firefox, and WebKit development/CSP-production flows observe a multipart boundary, text field, picked filename, one request, and typed response; the preceding file read separately verifies bytes |

## 0.8D checked rest parameters

| Contract | Evidence |
| --- | --- |
| Variadic calls remain concise | A final `...values: T` parameter accepts ordinary repeated arguments and explicit `...List<T>` call expansion |
| The body keeps one simple type | The rest name is an immutable `List<T>` binding; the annotation denotes the element rather than a second array-wrapper syntax |
| Invalid declarations fail early | Missing element types, default values, following parameters, component rest props, and class-constructor rest parameters produce `VEL2016` diagnostics |
| Calls retain static checks | Every ordinary variadic argument and spread-list element must match `T`; required fixed arguments must be supplied before a spread |
| JavaScript semantics stay native | Named functions, instance/static methods, arrows, and extern declarations lower to or describe native JavaScript rest parameters without an arguments-object shim |
| Inheritance remains exact | Rest presence and element type are part of a method signature, so an incompatible override is rejected |
| Modules and editor semantics agree | Exported rest element types survive project interfaces, imported class renaming, semantic symbol types, and signature help |
| Safe npm interop recognizes the same shape | A final array-typed rest parameter in a supported `.d.ts` function or callback maps to the Velar rest element type; unsupported declarations still degrade to `unknown` |

## 0.8E native Set collection

| Contract | Evidence |
| --- | --- |
| Construction stays clean | `Set()` creates an inferred empty collection and `Set(list)` copies a checked List; source never writes a generic constructor call |
| JavaScript identity is retained | Emission uses native `new Set`, SameValueZero membership, insertion-order iteration, and native reference identity rather than a parallel runtime collection |
| The public surface is deliberately small | `size`, `add`, `has`, `remove`, `clear`, and `for` iteration cover the first contract; `add`/`clear` normalize their result to Velar `none` |
| Empty local inference reaches tooling | The first typed `add` refines `Set<unknown>` and updates the compiler semantic binding type used by hover and symbols |
| Types fail before runtime | Invalid constructors, later incompatible additions, incompatible annotations, malformed `Set<T>` arity, and attempts to shadow the Core binding produce diagnostics |
| Runtime data validation composes | `type` fields containing `Set<T>` validate the native container and every element through the existing emitted type authority |
| Modules retain element identity | Set element types, including imported class aliases, cross project interfaces and remain visible in LSP signature help |
| Safe JavaScript interop stays bounded | Supported `.d.ts` `Set<T>` and `ReadonlySet<T>` declarations map to the same Velar type; no ambient JavaScript Set global beyond the Core constructor is exposed |

## Compatibility versions

The current internal toolchain is `0.9.0-dev`. Standard API `0.4`, Web API
`0.7`, project format `2`, production build manifest format `2`, and LSP
protocol `1` define the active boundary. The project-format clean break uses
explicit extensions and requires no generic Workbench host change.

## 0.8F real-application language completion

| Contract | Evidence |
| --- | --- |
| Finite application states are closed | String-backed nominal `enum` values reject plain strings and foreign enum identities while remaining serializable and usable at string Web boundaries |
| Branches stay readable and complete | `match` accepts qualified enum members, diagnoses missing members without `else`, and treats a fully covered enum match as a complete return path |
| Modules preserve declaration identity | Direct imports, aliases, transitive reactive exports, runtime parsing, hover, completion, definition, references, and safe rename resolve the original enum declaration rather than comparing display names |
| Collection use is complete enough for applications | `in`, Map copy plus key/value/entry List snapshots, and Set value snapshots are typed and lower to native JavaScript order/identity semantics |
| IDs do not require unsafe workarounds | Standard API 0.4 adds `velar/id.uuid()` and `isUuid()`; UUID generation requires the secure host capability and never falls back to timestamps or `Math.random` |
| A separate real app owns the pressure test | FlowBoard performs task creation, finite workflow transitions, deletion, search, enum select binding, local persistence, lazy analytics, Map-derived priority summaries, reload recovery, and production build verification |
| Browser behavior is portable | FlowBoard's CRUD, persistence, filtering, enum selection, and lazy route tests pass Chromium, Firefox, and WebKit through `velar test --browser` |
| Workbench remains an injected host | Only the Velar contribution gains the enum keyword; the generic Workbench host stays language-neutral, its focused nine-test language suite passes, and a packed installed toolchain returns enum completion/hover/definition/references/rename through the shared LSP path |

## Deferred release work

This gate deliberately does not create a repository, commit, tag, release
candidate, npm publication, hosted preview, or provider configuration. Those
remain separate user-authorized activities. Production-readiness still
requires external use evidence and the release-integrity decisions tracked in
[production-readiness.md](production-readiness.md).
