# VelarScript 1.0 Internal Acceptance Matrix

Status: internal engineering gate complete; external preview and release evidence pending

This matrix records the evidence available before VelarScript is exposed to
independent users. It closes the repository-owned 1.0 audit, but it is not a
production-ready or release claim. Apache-2.0 now covers the workspace and both
packed toolchain packages. A public claim additionally requires stable
versioned source, an authorized remote and tag, a live
preview, independent application use, compatibility feedback, and an audited
release candidate.

## Requirement-to-evidence matrix

| Requirement | Internal evidence | Gate |
| --- | --- | --- |
| Language semantics are defined by Velar rather than JavaScript accidents | Compiler execution and diagnostics cover strict values, optionals, control flow, functions, async/await, Promise adoption, arithmetic and power precedence, comparison chains, collections, modules, JSX, runtime Types, classes, inheritance, `init:`, native `private`, and read-only getters. A deterministic malformed-input corpus exercises compile, inspect, and format APIs without allowing internal exceptions to escape. The language charter records the accepted surface. | Passing internally |
| Source modules and JavaScript interop preserve checked identity | Cross-module source packages, dynamic `.vel` imports, JavaScript npm packages, bounded `.d.ts` graphs, native classes, aliases, inheritance, and nominal identities run through compiler, package, and LSP tests. | Passing internally |
| Web applications own failures and cleanup | Release Studio exercises route, event, render, resource, action, HTTP cancellation, logging, and recovery paths. Hostile HTTP, file, realtime, form, route, browser-helper, storage, and IndexedDB values are rejected before unsafe side effects or through their owned asynchronous channel. The development server contains an unexpected watched rebuild failure, retains the last good application, reports the failure through status/SSE, recovers on the next edit, and converges after a 64-write burst. | Passing internally |
| JSX, reactivity, components, and browser output are portable | Development and verified CSP production suites pass Chromium, Firefox, and WebKit. SVG/HTML namespace transitions, accessibility diagnostics, lazy chunks, actions, resources, keyed updates, and cleanup are covered by real applications. | Passing internally |
| Real applications pressure the language instead of serving as syntax demos | FlowBoard covers finite state, collections, persistence, callbacks, lazy analytics, and equality; SupportDesk covers routing, native forms, resources, recovery, persistence, and dialogs; API Dashboard covers typed HTTP, npm interop, classes, getters, SVG, lazy components, and concurrent async work. Their Core and browser suites are part of the root gates. | Passing internally |
| A new team project works from installed packages | `tests/package.acceptance.ts` packs and installs the compiler and CLI, exercises the CLI and compiler API, and checks package contents. `tests/installed-browser.acceptance.ts` creates a fresh project from packed packages and runs its generated format, check, Core test, build, verify, and Chromium browser scripts. | Passing internally |
| Compiler and editor remain independent | The compiler LSP owns diagnostics, completion, hover, signatures, navigation, references, rename, formatting, type hints, semantic tokens, code actions, and commands. The generic Workbench host consumes the packed toolchain through the injected Velar contribution; the installed gate and 9 focused host tests pass without a Workbench-owned type system. | Passing internally |
| Application-scale compilation has an explicit budget | `tests/performance.test.ts` checks a 121-module initial build and an incremental change that recompiles only the 41-module reverse-dependency closure while reusing 80 modules, under the checked time budgets. Project-session tests additionally remove and restore a dependency while preserving an unrelated compiled module. | Passing internally |
| Production output is exact and reproducible | Browser-project acceptance builds and verifies production output. Release acceptance checks byte-identical package identities and a reproducible root Netlify preview across separate directories. Manifest tampering, extra files, traversal, unsafe replacement, and mismatched release sets fail closed. | Passing internally |
| Release tooling cannot silently publish the wrong source | Rehearsal creates verified tarballs and manifests without publishing. Candidate mode requires a stable version, committed clean source, exact tag, matching origin, publishable licenses, exact artifacts, and explicit publish authority; the current development tree intentionally fails those conditions. | Passing internally; public candidate pending |
| Production behavior is observed outside repository-owned examples | A live hosted preview is verified from another network and browser context; independent users build and operate applications; resulting compatibility issues become regression tests. | External evidence required |

## Authoritative gates

Run from the VelarScript repository:

```text
npm run check
npm test
npm run test:packages
npm run test:browser
npm run release:rehearse
npm run release:verify -- release/rehearsal
```

Run from the independent Workbench repository against the rehearsal manifest:

```text
bun test tests/language-support.test.ts
bun scripts/test/verifyInstalledVelarToolchain.ts <absolute-release-directory>
```

The compiler/CLI gate currently contains 190 tests before the three real Core
application suites. The browser gate separately covers development, verified
CSP production, all three real applications, and a freshly generated project.
Counts are supporting detail; the commands and named contracts above are the
acceptance authority.

## Remaining external gate

The following work is intentionally not inferred from green local tests:

1. create the first attributable source commit while retaining the development version;
2. configure the intended remote and push that source identity;
3. after external feedback, choose the stable version, create the exact version tag, and audit the
   clean release candidate;
4. explicitly authorize npm publication and hosted preview deployment;
5. verify the live deployment and collect independent application feedback;
6. convert every release-blocking compatibility finding into a retained test.

Until those items have evidence, describe VelarScript as **internally accepted
for external preview**, not production-ready.
