## 第 89 条 —— 错误的可判别性：类是唯一分类，`code` 是它的字符串投影（D39-55 定案）

### 阻塞点回顾

D39-55 只批了原则（「官方 Error 家族带稳定 readonly `code: string`」），
缺六样东西：家族 roster、既有抛错到 code 的映射、code 字符集/前缀、同 code 的
参数化边界、原生 `TypeError`/`RangeError` 的处置、跨 Core/Web/Node 的版本规则。
Codex 因此正确拒绝实现（不擅自造事实标准）。

### 裁决：不引入平行分类法

**一个错误只有一套分类：它的类。** `code` **不是**第二套 taxonomy，而是类身份
的**字符串投影**，由编译器自动提供，等于该错误类的**声明名**：

```
catch error:
    if error is FileNotFoundError:        // 语言内的判别拼写（唯一）
        ...
    log(error.code)                        // "FileNotFoundError" —— 同一身份的字符串形
```

这一条同时回答了 Codex 列出的全部六个缺口：

| 缺口 | 答案 |
|---|---|
| 家族 roster | **错误类层级本身**（下条系统导出） |
| 抛错 → code 映射 | **恒等映射**，无需维护、不可能漂移 |
| 字符集/前缀 | 类名规则（已成文：PascalCase 标识符） |
| 同 code 的参数化 | 不适用 —— 细节住在**字段**里（`path`、`status`…），不进 code |
| 原生 TypeError/RangeError | 宿主错误在边界归一化；其 code 是包装它的 Vel 类名，无包装则 `"Error"` |
| 版本规则 | 类名即 API；改名是破坏性变更，与语言其余部分同规（Vel 永不承诺兼容） |

**为什么不做平行 code roster**：那会制造第二套判别机制 —— 规则 3 违例。
类已经可判别（`is` 收窄、ValidationError/NarrowingError/IndexError 已可命名），
再发明一套字符串常量表只会让 AI 在两种拼写间摇摆。`code` 的正当用途只有
**序列化与日志**（类身份跨不过 JSON 边界），恒等投影正好满足且零维护。

### 落地要求

1. **`code: string` 只读成员**加入 checked `Error` 契约（与 `message`、`cause`
   并列），值 = 该实例的声明类名，编译器在类降级时提供（第 74 条已让 Error
   子类设置 `.name`，`code` 与之同源，二者不得分叉 —— 实现须共用一处真相）。
2. **stdlib 错误类家族系统导出**（方法学同 D41 的约束词汇：**反查代码而非想象**）：
   遍历 `packages/cli/src/standard-modules.ts`、`packages/node/**`、
   `packages/web/**`、`packages/desktop/**` 的**每一处抛错点**，按「**调用方
   会写出不同恢复逻辑**」归组 —— 同一恢复对应一个类，不同恢复必须分类。
   预期形态（实施者按实际抛错点定案，多退少补）：
   `velar/fs` → `FileNotFoundError`、`PermissionError`、`NotADirectoryError`；
   `velar/http` → `RequestFailedError`（带 `status`）、`NetworkError`、`TimeoutError`；
   `velar/serve`、`velar/terminal`、`velar/process` 同法。
   **每个新类必须有一个真实抛错点** —— 不为对称而造类。
3. **可命名**：三个既有内建（Validation/Narrowing/Index）已可命名，新类同规
   （`catch` 内 `is` 判别、不可被用户继承）。
4. **不做的**：不引入 code 常量表、不引入 code 命名空间、不改原生 JS 错误的
   身份、不为「未来可能的错误」预留类。
5. 文档：charter §11 增补一节（错误判别 = 类；`code` 是其字符串形）；
   standard-library.md 每个模块列出它会抛的类；AI 简报一行。

## 第 90 条 —— 纯计算全部常驻：`Json` 补全、`Text` 建立、`deepEqual` 退役（D35 冲突定案）

### 冲突回顾

D35 写「velar/json 全量常驻」并要求「velar/text 最终方法化清空」；批次 K 的
任务书只列了四个 Json 成员、未动 text。两处文字冲突。

### 裁决

**统一原则（D35 的「能算的不用导，能碰外界的必须导」全面执行）：**
**每一个纯计算函数都进常驻命名空间；每一个碰外界的能力保持显式 import。**

1. **`Json` 补全为全量**：批次 K 已落的 `parse`/`stringify`/`stableStringify`/
   `clone` 之外，`tryParse`、`isSerializable` 一并常驻。`velar/json` 的具名
   导入全部退役（迁移诊断）。
2. **`Json.deepEqual` 退役，`equals` 是唯一拼写**（N-3 一致性扫发现的双拼写）。
   实施者须**先实测两者的语义差异**：若 `deepEqual` 有 `equals` 不具备的能力
   （如仅接受 JSON 值域、或不同的 NaN/-0 处置），**扩展 `equals` 吸收之**，
   不得保留两个函数；差异若纯属实现细节则直接删。理由：内容比较是一个概念。
3. **建立 `Text.` 常驻命名空间**，收纳 `velar/text` 的全部纯函数
   （slug、escapeHtml、utf8Size、lineStarts、chunks、dedent、truncate、title、
   capitalize、normalizeWhitespace、lines、模式操作族…），`velar/text` 的具名
   导入退役。
   **推翻 D35 的「Text. 不建、改用方法」**，理由具体：把 20 个函数方法化会让
   核心字符串成员表**翻倍**（现 18 个，全是高频操作），迫使每个 AI 背下
   `utf8Size`/`lineStarts` 这类多数程序永不触碰的成员；而 `Text.` 给它们一个
   零导入、可发现、与 `Json.`/`Promise.`/`Look.` 一致的家。核心字符串方法表
   **保持不变**（不新增、不迁出），规则一句话：**「字符串方法是核心操作，
   `Text.*` 是扩展工具箱」**。命名冲突不存在 —— 类型名是小写 `string`。
4. **TXT-U4 的 `codePoint`/`fromCodePoint`** 随本条落在 `Text.` 下
   （代理半拒收，见文本审计）。
5. **能力模块不变**：`velar/fs`、`http`、`storage`、`browser`、`serve`、
   `terminal`、`process`、`app`、`forms`、`web-test` 全部保持显式 import。
6. 文档：charter 的常驻命名空间小节列全四个（Json/Promise/Text/Look）与该
   一句话规则；standard-library.md 重排为「常驻纯计算」与「须导入的能力」两部分；
   AI 简报的常驻段落补 `Text.`。

## 第 94 条 —— `case` 与 `enum` 是 JS 保留字，不可作绑定名（波 G 上报，裁决确认）

波 G 执行级证明（本编排代理独立复验：`node -e "eval('const case = 1')"` 与
`enum` 同样 `SyntaxError`）：**`case` 与 `enum` 都是 ECMAScript 保留字**，
作为 Vel 绑定名会发射出 Node 拒绝解析的 JS。

- **D30 第 16 条把 `case` 与 `match` 一并归入「JS 不保留、可软化」是分类错误**，
  并给出 `for case in cases:` 作目标 —— 该目标不可达。D30 自己为 `enum` 写的
  理由逐字适用于 `case`。
- **本编排代理给波 G 的任务书把 `enum` 列进「必须可作绑定名」同样是错的**，
  与 D30 的既有裁决冲突；波 G 按 D30 执行是对的。

**裁决（确认波 G 的处置）**：`case` 与 `enum` 在 Vel 内**照常软化**（记录字段、
成员名、match 分支、成员访问全部可用），但**不可作绑定名**，诊断说出真实原因
（「`case` 是 JavaScript 保留字，产物无法解析」）。

**明确排除的替代方案**：让发射器重命名源绑定。它与 charter §19 及「产物是可读
的逃生通道」这一产品承诺相抵 —— 用户读发射产物时看到的名字必须是他写的名字。
两条硬保留名的代价（两个词）远小于「产物名字会被悄悄改写」的代价。

同理适用于将来任何被发现是 JS 保留字的候选词：**软化的边界由母亲的保留字表
划定，不由我们的愿望划定**。

## 第 95 条 —— 字符串成员指引按「行为保持」判据拆表（波 L 上报，裁决）

波 L 正确地拒绝把 `stringMemberGuidance` 整表并入 `velar fix` 家族并上报：
该表混着两类性质不同的条目。裁决**不是新设计，是把家族既有判据施加到这张表**：

**判据（D38 第 48 条已定）**：只有**可证行为保持**的替换进 `velar fix`；
凡替换会改变实参含义、单位、或结果类型的，**留作诊断教学**。

逐类归属：

| 类别 | 例 | 归属 | 理由 |
|---|---|---|---|
| 纯改名（同参同义同结果） | `toUpperCase` → `upper`、`toLowerCase` → `lower`、`includes` → `has`、`trimStart` → `trimStart`… | **进家族** | 机械替换，语义逐位相同 |
| 后继是常驻命名空间成员 | `normalize` 等 → `Text.*`（第 90 条落地后） | **进家族** | 同上；替换文本含命名空间前缀 |
| **实参含义改变** | `substr(start, length)` → `slice(start, end)` | **不进** | 第二参数从「长度」变「终点」—— 机械替换会**静默改变行为**，正是 MIG-1 点名的最坏诊断类 |
| **单位改变** | `length` → `size` | **不进** | UTF-16 码元 vs 码点：ASCII 上恰好相等、含 emoji 时不等 —— 「多数情况下对」的修复比不修复更危险 |

后两类的诊断**必须说出差异本身**（不只是「用 X 代替」）：
「`substr` 的第二个参数是长度，`slice` 的是终点位置 —— 请换算后改写」；
「`length` 数 UTF-16 码元，`size` 数码点 —— 含非 BMP 字符时两者不同」。

**通则记档**：`velar fix` 的家族边界不是「诊断能不能给出替换文本」，而是
**「替换是否可证等价」**。能给出正路但不等价的诊断，正路进消息、不进自动修复。

## 第 96 条 —— 波 M 的四处上报裁决（2026-08-14）

**1. D41 实现风险 3 已过期（无需动作）**：D42 早已把六个有序性判定点合并为
一处权威，`Comparable` 因此只花一个分支而非预测的最坏情况。**记档意义**：
规格里的风险评估会被后续波次的成果作废 —— 实施者按现状而非按规格的旧世界
判断是对的。副作用（`sorted(by=)` 的选择器**形状**按可赋性判、**键**按有序性
权威判）是正确的分工。

**2. 能力面的可释放性用结构判定，不用类型名清单（确认实施者裁决）**：
把 `FileWatcher`/`Server` 等类型名写进 Core 会破坏 charter 规则 5（Core 不认识
能力模块）。实施规则：**identity 以 `velar/` 开头的 named 类型**（用户类型是
`velar:<path>#…`，结构上不可能碰撞）**且恰有一个零参 `close`/`stop` 返回
`null`/`Promise<null>`**。覆盖全部六个具名句柄，记录永不匹配。**确认** ——
这正是 D43 第 69 条「能力 API 不改名」承诺的正确实现形态。

**3. `using` 在组件体内拒绝 —— 推翻 D43 第 69 条的「组件体合法」（我的规格错了）**：

实施者的理由成立且比我的原文更清楚：**组件体是构造，不是作用域**。它的
「退出」不在最后一条语句，而在卸载。于是 `using` 在组件体内只有两种可能语义：
(a) setup 结束即释放 —— 错的，资源在组件整个生命期都要用；
(b) 卸载时释放 —— 对的，但**那正是 `@cleanup:` 已经拥有的东西**。

选 (b) 会让 `using` **按位置改变含义**（块内=块退出释放、组件体内=卸载释放）
—— 正是用户当初否决 `%` 标量徽章模型的那一类陷阱（「同一表达式换位置」测试）。

**裁决**：组件体内 `using` 拒绝，诊断教 `@cleanup:`。两个生命期、两个拼写、
零重叠：**`using` = 块作用域释放；`@cleanup:` = 组件生命期释放**。组件内的
action 与方法体照常支持 `using`（它们是真作用域）。charter §16 与 D43 第 69 条
第 6 项按本条更正。

**4. 两处超出 `try` 规格字面的拒绝（确认）**：`null` 值的成功、未 await 的
Promise。两者都是规格自身「禁止裸 `try` 语句」理由的延伸 —— `try` 表达式的
值必须**携带信息**：恒 `null` 的成功与失败无从分辨；未 await 的 Promise 会让
`try` 抓不到真正的异步失败（抓到的只是「成功地得到了一个将来会失败的东西」）。
**确认保留**，且这两条诊断必须说出该理由本身。

## 第 97 条 —— 波 R2 的三处上报裁决（2026-08-14）

### 1. 常驻的准入规则：纯度是**资格**，普遍性是**准入**

波 R2 正确指出第 90 条的措辞「每一个纯计算函数都进常驻」与四命名空间名册
自相矛盾：`velar/collections`、`velar/math`、`velar/url` 同样是纯计算却仍需导入
（`velar/time`、`velar/id`、`velar/log` 不是纯的 —— 它们碰时钟、熵、外界，
要求导入正确）。

**裁决 —— 两段式规则，修正第 90 条的措辞**：

> **纯度决定一个模块是否*可以*常驻；普遍性决定它是否*应当*常驻。**

理由：常驻的代价不是安全性（纯函数没有能力风险），而是**先验负担** ——
每一个常驻名字都是 AI 必须不经提示就知道的名字，也是简报预算里的一行。
Json（数据变文本）、Promise（异步组合）、Text（字符串工具箱）、Look（视觉构建）
是**几乎每个程序都会碰**的四个工具箱；collections/math/url 是**刻意去取**的
专门工具，一行 import 恰好表达了「我选用了这个工具箱」这个信息。

**未来准入门槛**：一个模块要进常驻，须同时满足「纯计算」与「近乎每个程序都用」。
只满足前者的保持 import —— 这是决定，不是遗漏。

### 2. `velar/test` 的 `toEqual` 必须改用 `equals`（新工单）

波 R2 实测：`toEqual` 仍用已删除的那份比较实现，在 **NaN、Set-of-records、
>512 层深度**三处与 `equals` 给出**不同答案**。裁决理由与 `deepEqual` 退役
完全相同、且更急迫：**断言给出与语言自身相等语义不同的答案，是测试框架最坏的
陷阱**（测试通过而程序错，或反之）。

**裁决**：`toEqual` 改由 `equals` 实现，一处真相。归收尾波。

### 3. 命名空间导入必须与具名导入同样退役（新工单）

`import * as text from "velar/text"` 今天仍合法，绕过了具名说明符的退役诊断 ——
批次 K 对 `velar/json`/`velar/async` 留了同一个洞。**裁决**：退役的模块，其
**命名空间导入**得到同一条迁移诊断。理由：退役的目的是消灭第二个拼写，留着
命名空间形等于退役没有发生。归收尾波。

### 4. 附带确认（波 R2 的判断正确，无需改动）

- **`deepEqual` 直接删除**：实测它没有一处能力是 `equals` 不具备的，反而在四处
  给出**更弱或错误**的答案（NaN 判不等与 D42 矛盾；Set/Map 仅按身份；600 层
  相同结构静默 `false`；环静默 `false`）。「唯一独有」的是静态接受 `any`/`unknown`
  —— 那是绕开 D47 的 parse-first 纪律，删掉恰好把纪律补回。
- **错误类只给五个**：数百个实参/预算违例、数十个宿主协议违例的恢复都只有
  「改代码」一种，**一个类都不给**是对的 —— 第 89 条「每个类必须有真实抛错点
  且对应不同恢复」的严格执行。
- **`velar/http` 的三个既有类不改名**：改名 churn 公开面而不带来新恢复能力。
- **`code` 不做储存属性**：读 `code` 降级为读实例自有的 `name`（第 74 条写进去
  的那一个），二者分叉在结构上不可能；副作用是挡住了宿主 errno 冒充
  （Node 的 `.code === "ENOENT"` 不会漏进 Vel 的词汇）—— 这个副作用是**收益**。

## 第 98 条 —— AI 简报预算上调至 750 行（一次性，附纪律）

**触发**：波 G、M、R2 连续三波撞上 600 行上限，每次都逼我删掉**真内容**
（类型约束的解释被压成一句、项目搭建章被反复压缩）。当"为了凑数字而删有用的
东西"发生第三次时，该被审视的是数字。

**技术约束不存在**：600 行 ≈ 7k token，750 行 ≈ 9k —— 在 200k 上下文里都不构成
压力。预算从来不是为了装得下。

**预算的真实用途是强迫排序**：每一条进简报的内容都要挤掉另一条。这个纪律有效
且必须保留 —— 波 M 的类型约束压缩就是它的正确产物（约束是库作者写泛型辅助
函数时用的，绝大多数应用代码永不触及，压成一句是对的排序）。

**裁决**：上限改为 **750 行**，且**纪律写进测试的失败消息本身**：
「撞到上限时删最不需要的内容，不要抬上限 —— 长尾属于诊断」。
理由：语言在本轮马拉松中增加了四个语法特性、两个常驻命名空间、以及盲测证明
必需的项目搭建章；简报覆盖面实质变大，而它的**信噪比没有下降**。

**不再上调**：下一次撞到 750 时的正确动作是砍长尾，不是再抬。若长尾已砍尽仍
超限，那意味着语言表面本身过大 —— 那时该被审视的是语言，不是简报。

## 第 99 条 —— 副作用导入：两种拼写都拒绝，教显式调用（推翻我在审计账本里的 MOD-I2 决案）

波 Z1 上报规格互相冲突：D31 第 28.3 条说副作用导入**保持不支持**并给定向拒绝；
我在审计账本 MOD-I2 处却裁了「祝福裸字符串形」。D31 那条从未实现，所以现状是
`import "./fx.vel"` 报无关的默认导入错误、而 `import {} from "./fx.vel"` **合法
且会跑副作用**。

### 裁决：拒绝两种拼写

**理由（与 D43 第 68 条排除装饰器完全同源）**：副作用导入是**隐形动作**。
读者看到 `import "./setup.vel"` 无法知道发生了什么 —— 必须去读那个模块。
我排除用户自定义装饰器时给的理由是「一个库不能改变某个声明的含义」，
副作用导入同样把行为藏在读者看不见的地方。**使命是「AI 写、人来读」**，
一行看不出效果的导入正是要拔掉的东西。

我原先祝福它的理由是「双亲都有」—— 但那条从来不是无条件的：Vel 已经删掉过
双亲都有的真值判断、`==` 强转、`switch`。**双亲有某能力不等于该能力不是陷阱。**

### 目标语义

- `import "./fx.vel"` 与 `import {} from "./fx.vel"` **都拒绝**，一条定向诊断：
  「模块的效果要看得见：导出一个函数并调用它 —— `import {install} from
  "./fx.vel"` 再 `install()`」。
- `import css unsafe "./x.css"` **不受影响**（它是已裁决的资源边界，且 CSS
  没有可调用的等价物）。
- charter 第 28.3 条的原意由此兑现；账本的 MOD-I2 决案作废，本条替代。
- 波 Z1 已实现的「祝福裸字符串形」需要回退为本条的双拒绝。

### 附带确认（波 Z1 的两处判断正确）

1. **它修了一个「已批准裁决所推荐的替代方案本身不可用」的缺陷**：D45-78 的消息
   教作者「把实例放进字段」以替代继承 extern 类 —— 而 extern 类名出现在**类字段
   或记录字段**注解里时会冻成结构化命名类型，声明看着干净、**成员读取**才报
   「Type 'Chart' has no field 'draw'」。这与 BRG-D2 是同一种静默桥退化。
   **教出去的路必须走得通**，这个顺手修是正确的越界。
2. **LOK-I5 的第一版与既定契约冲突时，既有契约胜**：让 Core 无条件吞 `%` 会
   破坏「两种取余拼写都求值为 1」这条钉住的契约；改为只在不可能跟取余操作数的
   位置（行尾、`)`、`]`、`,`）把 `50%` 读作单位 —— 正确的取舍顺序。
