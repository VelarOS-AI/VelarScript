# D42 — 相等与有序的统一收紧（已批准，待实施）

用户于 2026-08-12 裁决：「number 不能和 string 做比较」→ 批准完整规则。
本文把相等与有序两处收紧合成**一条原则**，因为它们的根因相同：

> **不可能相交的类型之间的比较，其结果恒定 —— 那不是强转 bug，是静默逻辑
> bug，正是使命要拔掉的东西。**

判据同 D28-D41。全部现状结论均由真编译器探针实测。

## 第 64 条 —— `==`/`!=` 要求操作数类型有交集（归批次 A′）

### 现状（实测：相等对类型零检查）

```
1 == "1"        → 编译通过（运行 false）
user == "a"     → 编译通过（记录 vs 字符串，永假）
true == 1       → 编译通过（永假）
A.x == B.x      → 编译通过且运行 **true**（跨枚举，见第 65 条）
```

`analyzer.ts:3578` 无条件返回 `boolType`；只有有序比较 `<` 在查类型。
Vel 当年去掉 JS 强制转换让 `==` 变严格，但严格比较两个不可能相交的类型
**恒为假** —— 从「强转 bug」换成了「静默逻辑 bug」，净收益为零。
TS 对 `1 === "1"` 报错（no overlap）是现成先例。

### 目标语义

**规则**：`==` / `!=` 要求两操作数类型**有交集**（任一方可赋给另一方，
按既有 `isAssignable` 判定，先展开别名与可选）；无交集 → 编译错误。
消息教「这两个类型无交集，比较恒为假」并点名双方类型。

**完整情形表**（穷尽枚举，含必须小心的两处）：

| 情形 | 判定 | 说明 |
|---|---|---|
| `number == string`、`bool == number`、记录 vs 原始值 | ✗ 拒绝 | 用户裁决的直接目标 |
| **`T? == null`、`user == null`** | ✓ **必须保留** | 空值判断的唯一拼写（D30 第 22 条）—— `null` 天然在 `T?` 的域内，用可赋性判交集自动成立 |
| `T == null`（T 非可选） | ✗ 拒绝 | 永假的冗余检查，抓真 bug（消息教「T 不可为 null」） |
| `A.x == B.x`（跨枚举） | ✗ 拒绝 | 见第 65 条：同时修掉标称身份的洞 |
| `status == Status.done`（status: Status） | ✓ | 声明类型有交集 |
| 收窄后 `Status.pending == Status.done` | ✗ 拒绝 | 已收窄则确实恒假；**else 分支收窄为联合、仍有交集，不误伤** |
| `User == Order`（结构相同的两记录） | ✓ | **用可赋性判交集、不用名字** —— 结构相同即有交集 |
| `List<number> == List<string>` | ✗ 拒绝 | 元素类型无交集 |
| `unknown` / `any` 任一侧 | ✓ | 不安全边界照旧放行 |
| 联合含交集成员（`(string \| number) == string`） | ✓ | 部分交集即可 |

- 运行时语义**不变**（SameValueZero 降级不动，D36 第 41 条）；本条纯静态收紧。
- 迁移：全仓门禁为准。每一处被拒的站点都是「恒为假的比较」= 真 bug 或死代码。
- charter §4 相等段落成文；AI 简报加一行；典章第 2 节（空值纪律）确认不受影响。
- 回归：情形表逐行（含 `T? == null` 与 else 分支收窄两处防误伤的正面断言）、
  `!=` 同规则、跨模块同名不同源记录按可赋性判定、`unknown`/`any` 放行。

## 第 65 条 —— 枚举不算 `Comparable`，跨枚举比较被拒（归批次 A′）

### 现状（实测：枚举的标称身份在运行时不存在）

```
A.x == B.x                                  → true      （跨枚举相等）
[A.x, B.p].sorted()                         → ['p','x'] （跨枚举排序）
List<A | string>.sorted()                   → ['raw','x'] （枚举与裸字符串混排）
[Priority.high, .low, .normal].sorted()     → [high, low, normal]  ← **字母序，静默错序**
```

根因：**枚举在运行时就是裸字符串，标称身份只活在类型层**。charter §6 承诺
「`EventKind.text` 是标称单例、不是开放字符串」，在**相等与排序这两个运行时
操作上不成立**。

### 目标语义

1. **跨枚举相等**：由第 64 条的交集规则自动拒绝（不同枚举无交集）。

2. **枚举 vs `string` 相等：显式例外，必须拒绝**（已实测核实，理由已定案）。

   实测现状：`const s: string = K.a` 合法（W-54 的用途），`K.a == "wire-a"`
   **今天为 true**。因此纯「可赋性判交集」的规则会让它合法 —— 这是第 64 条
   通用规则**唯一失效**处，需要显式例外。

   **理由（方向性，不是「按声明类型」那么弱）**：枚举 → `string` 的可赋性是
   **单向出口**，为「把线上值发出去」服务（`request(kind)`）。反向（裸字符串
   进入枚举域）必须经 `Enum.parse` 验证 —— charter §6「开放字符串不会静默
   成为枚举成员」。而**相等是对称的**：允许 `raw == Kind.textDelta` 就等于
   开了一条**绕过 `parse` 的读入路径**，把单向便利偷偷变双向。

   诊断教正路：`Kind.parse(raw) == Kind.textDelta`（先验证再标称比较）；
   确实只想比字符串则 `raw == str(Kind.textDelta)`（显式降级为字符串比较）。

   实施注意：交集判定不能只调 `isAssignable`，必须先排除「一侧是枚举/枚举
   成员、另一侧是 `string`」这一组合。

3. **枚举不进 `Comparable`**（D41 第 61 条的完整词汇据此定案）：
   - `sorted()` / `sorted(by=)` / `sortBy` / `minBy` / `maxBy` 的键类型收紧为
     **`number` 或 `string`，且同类别**（即统一到最严的 `isCollectionOrderKey`）。
   - 直接 `<` `>` `<=` `>=` 维持拒绝枚举（现状已正确）。
   - `min()` / `max()` 维持拒绝枚举（现状已正确 —— ORD-2 因此**不是**误拒，
     而是三谓词中唯一正确的那个）。
   - **`Comparable` = {`number`, `string`, 同类别联合}**。
4. **业务排序的显式出路**（诊断必须教）：`sorted(by=rank)` 给显式序，或用
   字符串背书枚举把序编进运行时值（`enum P: low = "1-low"` 之类）。
5. 破坏性变更诚实标注：今天能跑的 `List<Status>.sorted()` 会开始报错 ——
   **但它本来就在给字母序，即错序**。CHANGELOG 必须写明这一点。

### 顺带关闭的三条排序谓词不一致（账本 ORD-1/2/3）

| ID | 关闭方式 |
|---|---|
| ORD-1（`List<number \| string>.sorted()` 编译通过、运行抛错） | `defaultSortableType`（analyzer.ts:7116）的 `members.every` 改为要求 `categories.size === 1`，与 `isCollectionOrderKey` 统一 |
| ORD-2（`List<Status>.min()` 被拒） | **维持拒绝** —— 它是三者中唯一正确的；改的是另两个 |
| ORD-3（直接 `<` 拒绝枚举但排序接受 + 静默字母序） | 排序路径收紧到与直接 `<` 一致 |

三个谓词（`analyzer.ts:3650` 直接 kind 检查、`7116`/`7122` 两个近重复私有
谓词、`6484` `isCollectionOrderKey`）**必须合并为一个** —— 四套机制给三个答案
正是本组缺陷的结构性根因。实施要求：合并后全仓只剩一个「什么算有序」的判定点。

## 第 66 条 —— 与 D41 第 61 条的衔接

能力授予常量表不变。**第 64/65 条是批次 M 实现约束的前置**，必须先落地。
