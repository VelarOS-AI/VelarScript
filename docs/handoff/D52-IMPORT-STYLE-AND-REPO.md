不舒服」；并要求整理仓库（文档乱放、堆积历史、示例不佳、最佳实践缺具体例子）。

## 第 114 条 —— `Look.`/`Text.` 前缀取消，改回具名导入（部分推翻第 90 条）

### 裁决

**我们发明的前缀取消，镜像母语言的前缀保留。**

| 命名空间 | 处置 | 理由 |
|---|---|---|
| **`Look.`** | **取消** → `import {spacing, color, tracks, minmax, border, shadow, animate, …} from "velar/look"` | JS 里没有 `Look` 这个全局，前缀是我们发明的。且 look 块内是全语言最密集的调用位置，`Look.` 在那里纯粹是噪音 |
| **`Text.`** | **保留**（用户 2026-08-15 收窄范围：只改 Look） | 镜像规则本会判它取消，但用户明确只动 Look —— **这是所有者的取舍，不是从规则推出来的**，如实记录 |
| **`Json.`** | **保留** | 镜像 `JSON.stringify` —— 去掉前缀后 `stringify(x)` 单看不知道是 JSON 还是别的格式，**前缀携带信息** |
| **`Promise.`** | **保留** | `Promise.all` 就是全世界都认识的那个拼写；`all(...)` 更难读，且离母语言更远 |

**分界线一句话**：**前缀镜像母语言的保留**（`Json.`≈`JSON.`、`Promise.`≈`Promise.`）。
`Look.` 是我们发明且落在全语言最密集的调用位置，取消。`Text.` 按规则本该同去，
**用户选择保留** —— 记录为所有者的取舍，将来若有人问「为什么 Text 不一样」，
答案是「他觉得那样更好」，不是某条推导。

### 与既有裁决的关系（诚实标注）

- 第 90 条「每一个纯计算函数都进常驻命名空间」**部分推翻**：常驻命名空间保留，
  但只留 `Json.`/`Promise.` 两个。第 97.1 条的「纯度是资格、普遍性是准入」仍
  成立，只是**再加一道**：**前缀本身必须有存在的理由**——镜像母语言是理由，
  「统一好看」不是。
- 第 106 条（命名空间只作成员访问头）**范围缩小**到剩下的两个，规则本身不变。
- **具名导入的附带收益**（写下来供将来复核）：文件顶部的 import 列表**告诉读者
  这个文件用了什么视觉/文本词汇** —— 对「人来读」这条使命，这是零导入形态
  拿不到的信息。

### 落地要求

1. `velar/look` 恢复为**普通具名导入模块**；`Look` 作为常驻名字**退役**，
   并给出迁移诊断（`Look.spacing(...)` → 教 `import {spacing} from "velar/look"`）
   —— 与批次 K 当初反向退役的机制同一套。`Text`/`Json`/`Promise` 三个常驻
   命名空间**完全不动**。
2. 第 109 条的**保留类型名**中，`Text` 是否仍需保留？—— **仍需**：它是类型
   约束名（`<T: Text>`），与模块名无关。`Comparable`/`Data` 不变。
3. 全仓迁移：examples、stdlib `.vel`、docs 围栏、charter、AI 简报（双份逐字节
   一致）、`velar create` 模板。
4. 回归：具名导入可用、`Look.` 旧形态得到迁移诊断、`Text.`/`Json.`/`Promise.`
   三者均不回归、`velar fix` 能机械改写旧形态（前缀去除 + 补 import 是可证等价的）。

## 第 115 条 —— 仓库整理：开源仓库该有的样子

### 现状问题（用户点名 + 编排代理核实）

- `docs/` 12 份平铺，用户文档与内部文档混在一起（`compiler-architecture.md`、
  `runtime-boundary.md`、`release-process.md` 是**贡献者文档**，不是用户文档）
- **`docs/handoff/` 50 份内部工作账本**（D 系列裁决、审计账本、Codex 任务书）
  裸露在仓库里 —— 它们是马拉松的**过程记录**，对使用者是噪音
- `examples/` 里项目目录与散 `.vel` 文件混放（`core.vel`、`foundation.vel`、
  `inheritance.vel`、`standard-library.vel` 是**编译器测试语料**，不是示例）
- 最佳实践偏原则、缺**可复制的具体代码**

### 裁决：按读者分层

```
README.md              —— 一屏说清：这是什么、为谁、怎么开始
docs/
  getting-started.md   —— 装、建、跑、测（十分钟内出第一个应用）
  language.md          —— 语言参考（charter 的用户向重排）
  standard-library.md  —— 常驻 + 能力两部分
  web.md               —— 组件/JSX/Look/路由
  best-practices.md    —— 典章，每条配可复制的完整代码
  escape-hatches.md    —— 逃生通道（产品承诺，保留在显眼处）
  contributing/        —— 贡献者文档（架构、运行时边界、发布流程、CI）
  decisions/           —— D 系列裁决（历史，只读，给想知道「为什么」的人）
examples/
  <每个示例一个目录，README 说明它教什么>
```

- **`docs/handoff/` 的 50 份**：裁决类（D28-D52）移入 `docs/decisions/`；
  审计账本、Codex 任务书、波次报告是**过程产物**，移出仓库或归入
  `docs/decisions/archive/` 单一目录，不在顶层出现。
- **`examples/` 的散 `.vel` 文件**：它们被 `check:format` 等门禁引用，是语料
  不是示例 —— 移入 `tests/corpus/` 或同类位置，门禁引用同步更新。
- **示例重做**：每个示例有**明确教学目的**并在自己的 README 里写明；按最新
  典章与本文第 114 条的导入风格重写。
- **最佳实践**：每条原则后面跟**一段可直接复制运行的完整代码**（不是片段），
  且这些代码进文档门禁（本来就会编译）。

### 判据

一个第一次看到这个仓库的人（或 AI），**从 README 到跑起第一个应用不需要读
任何内部文档**；想知道「为什么这样设计」时，`docs/decisions/` 在那里等着。
